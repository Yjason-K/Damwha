# 2회차 — 반복 일정 저장 방식 기술 리뷰

**날짜:** 2026-06-22 (월) 10:00
**참석:** 박준영(PM), 김서연(백엔드), 이도현(프론트엔드), 최민지(디자인)
**목표:** 반복 규칙을 어떻게 저장할지 결정한다

> 심어둔 것 — 결정 1(규칙 저장 + 조회 시 전개, 예외는 별도 테이블), 이견 1(김서연↔이도현: 전개 저장 여부),
> 액션 3(김서연 마이그레이션 / 이도현 API 스펙 / 최민지 접근성 검토), 약속 1(김서연 금요일까지 벤치마크)
>
> **3회차 장애의 씨앗을 여기 심는다** — 알림 안건을 시간에 쫓겨 "일단 그대로 가고 나중에 보자"로 넘긴다.

박준영: 시작하겠습니다. 오늘은 서연님 스키마 설계안 보는 자리고요.

박준영: 네 저도요. 그건 나중에 짧게 보고, 먼저 서연님부터 하시죠.

[사이 2초]
김서연: 결론부터 말씀드리면 규칙만 저장하고 조회할 때 전개하는 방식으로 제안드립니다.
이도현: 아 전개를 안 하고요?
김서연: 저장할 때는 안 합니다.
김서연: 일정 테이블에 반복 규칙 문자열 하나를 넣고요, 예를 들면 매주 월요일이면 그 규칙 한 줄이에요.
김서연: 그리고 사용자가 유월 달력을 보면 그때 유월치를 계산해서 내려줍니다.
[겹침] 이도현: 음.
김서연: 지난주에 말씀드린 표준 포맷 그대로고요, 그걸 쓰면 나중에 매월 반복 얹어도 스키마가 안 바뀝니다.
[사이 2초]
이도현: 저는 그게 좀 걸리는데요.
김서연: 네 말씀하세요.
이도현: 그러면 프론트에서 일정 하나를 특정할 수가 없어요.
김서연: 어떤 상황에서요.
이도현: 예를 들어 칠월 육일 스크럼을 클릭했다고 치면, 그게 아이디가 뭐예요?
김서연: 반복 일정의 아이디랑 날짜 조합이요.
이도현: 그럼 지금 있는 화면 전부 고쳐야 되는데요.
이도현: 지금은 다 일정 아이디 하나로 돌아가거든요. 상세 열 때도 그렇고 수정할 때도 그렇고.
[겹침] 김서연: 아.
이도현: 그래서 저는 그냥 만들 때 전개해서 저장하는 게 낫다고 봐요.
이도현: 매주 반복이면 일 년치 오십이 개 행 만들어놓고, 각각 아이디 주고요.
이도현: 그러면 기존 코드가 하나도 안 바뀝니다.
[사이 3초]
김서연: 그건 되는데, 다만 몇 가지가 걸립니다.
[겹침] 이도현: 네.
김서연: 첫째로 규칙을 바꿀 때요. 매주 월요일을 매주 화요일로 바꾸면 오십이 개를 다 고쳐야 돼요.
이도현: 그건 뭐 한 번에 업데이트하면 되잖아요.
김서연: 그중에 이미 지나간 것도 있고, 개별로 수정된 것도 있어요.
김서연: 지난주 스크럼만 시간을 옮겼다고 하면, 그건 규칙 바꿀 때 같이 바꾸면 안 되죠.
[겹침] 이도현: 아.
김서연: 그걸 구분하려면 결국 "이건 규칙에서 나온 거고 이건 사람이 손댄 거다"를 표시해야 되는데요.
김서연: 그러면 규칙 저장하는 거랑 복잡도가 같아집니다.
[사이 2초]
김서연: 둘째로 끝이 없는 반복이요. 종료 날짜 없이 계속 반복이면 몇 개를 만들어야 되나요.
이도현: 어... 일 년치요?
김서연: 그럼 내년 유월에 사용자가 달력을 보면 아무것도 없습니다.
이도현: 아 그러네요.
김서연: 그럼 배치를 돌려서 계속 채워야 되는데, 그 배치가 또 하나의 시스템이 됩니다.
[사이 2초]
이도현: 음.
박준영: 도현님, 아이디 문제는 다른 방법이 없나요.
이도현: 어... 아이디를 합쳐서 만들면 되긴 해요.
이도현: 반복 아이디랑 날짜를 붙여서 하나의 문자열로요.
김서연: 그렇게 하면 됩니다. 그게 표준적인 방식이기도 하고요.
이도현: 근데 그러면 그거 파싱하는 게 프론트 여기저기 들어가는데요.
김서연: 한 군데로 모으면 되지 않나요. 아이디 만들고 푸는 함수 하나로요.
이도현: 그건 그렇죠.
[사이 2초]
최민지: 하나 여쭤봐도 될까요.

최민지: 사용자가 반복 일정 하나를 수정할 때요. 이번 것만 바꿀지 전체를 바꿀지 물어보잖아요.
김서연: 네 그게 예외 처리입니다.
최민지: 그게 어느 쪽으로 가든 다 필요한 거죠?
김서연: 네 둘 다 필요해요.
최민지: 그러면 그 부분은 어차피 새로 만들어야 되는 거네요.
[겹침] 이도현: 그렇죠.
최민지: 그러면 기존 코드가 안 바뀐다는 게 완전히는 아닌 거네요.
이도현: 어... 네 그건 맞아요.
[사이 3초]
박준영: 서연님, 조회할 때 전개하면 느려지지 않나요.
김서연: 그게 제일 큰 리스크예요.
김서연: 달력 한 달치를 볼 때 반복 일정이 백 개 있으면 백 개를 다 계산해야 되니까요.
박준영: 그게 얼마나 걸리는데요.
김서연: 그걸 아직 안 재봤습니다.
[겹침] 박준영: 음.
김서연: 이번 주에 재보겠습니다. 실제 데이터 크기로요.
박준영: 언제까지 가능하세요.
김서연: 금요일까지 벤치마크 결과 올릴게요.
박준영: 이십육일이요.
김서연: 네 이십육일.
박준영: 만약에 너무 느리면요?
김서연: 그러면 조회 결과를 캐시하는 걸로 갑니다. 그건 나중에 얹을 수 있어요.
김서연: 저장 방식을 바꾸는 것보다 훨씬 싸요.
박준영: 알겠습니다.

박준영: 그럼 정리하겠습니다.
박준영: 규칙만 저장하고 조회할 때 전개한다. 예외는 별도 테이블에 둔다.
박준영: 아이디는 반복 아이디랑 날짜를 합친 형태로 한다.
[겹침] 김서연: 네.
박준영: 도현님 괜찮으세요.
이도현: 네 아이디 함수 한 군데로 모으면 할 만할 것 같아요.
박준영: 성능은 금요일에 확인하고, 문제 있으면 캐시로 푼다.
김서연: 네 그렇게 하겠습니다.
[사이 3초]
박준영: 그리고 지난주에 넘긴 알림 얘기가 있었죠.
[겹침] 김서연: 아 네.

김서연: 네.
김서연: 지금 알림은 일정 하나에 알림 하나가 붙는 구조예요.

김서연: 네 그건 맞는데, 그걸 누가 언제 등록하느냐가 문제예요.

김서연: 그렇게 하면 되긴 하는데요.

김서연: 네 알겠습니다.
