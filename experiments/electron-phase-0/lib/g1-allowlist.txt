# G1 문자열 검사 허용 목록 (Task 3이 추가).
#
# check-macho.sh는 이 파일을 forbidden-strings.txt와 **함께** 읽는다. 여기 적힌
# (검사 대상 기준 상대 경로, 금지 문자열) 쌍에 해당하는 적중은 위반이 아니라
# `ALLOW`로 분류되어 **보고서에 근거와 함께 그대로 출력된다.** 숨기는 것이
# 아니라 분류하는 것이다 — 목록 자체가 커밋되고, 적중 건수와 근거가 매 회차
# 출력에 남는다.
#
# ## 왜 필요한가 (스펙 §4.1과의 긴장)
#
# 스펙 §4.1은 "어떤 파일에도 금지 문자열이 나타나지 않아야 한다"고 적었다.
# PostgreSQL처럼 **우리가 빌드하는** 산출물에는 그대로 성립한다 — Task 2가
# 위반 0건으로 끝냈다. 그런데 Python·ML 런타임은 우리가 빌드하지 않은 제3자
# wheel 수백 개와 CPython 표준 라이브러리 원본으로 이뤄져 있고, 거기에는
# 다음 네 종류의 금지 문자열이 **구조적으로** 들어 있다.
#
#   (a) 독스트링·예제·문서 메타데이터   예: site.py의 "/usr/local/lib/python2.5/…"
#   (b) 다른 플랫폼용 코드 분기          예: torch/backends/xeon/run_cpu.py (Linux)
#   (c) wheel 배포자의 빌드 머신 경로    예: scipy .so 안의 gcc 경로 문자열
#   (d) ctypes/dlopen 폴백 검색 목록     예: soundfile.py, ctypes/macholib/dyld.py
#
# (a)(b)(c)는 실행에 아무 영향이 없다. (d)만 실제 동작이며, 그것도 **번들 안의
# 라이브러리를 찾지 못했을 때만** 쓰이는 폴백이다. 그리고 CPython 자신이
# (a)(d)를 갖고 있으므로 — 어떤 CPython 배포본이든 마찬가지다 — 문자 그대로의
# "0건"은 Python 런타임에서는 달성 불가능하다.
#
# 그래서 Task 3은 셋을 갈랐다.
#   1. **재배치를 깨는 것**(STALE-PATH, OTOOL-L, LC_RPATH)은 전부 **고쳤다.**
#      허용 목록에 넣지 않았다. 이것이 P0-C3의 본론이다.
#   2. **번들에서 뺄 수 있는 것**(빌드 전용 트리, tkinter, pip)은 **뺐다.**
#   3. 남은 제3자·표준 라이브러리 원본 문자열만 이 파일에 **분류해 남긴다.**
#      (d)에 해당하는 항목은 아래에 `실동작-폴백`으로 표시했고, Phase 4가
#      확인해야 할 인계 항목이다.
#
# 실제로 로드되지 않는다는 것은 G2 dyld 실측(스펙 §4.2)과 P0-C8 런타임 자기
# 보고가 따로 확인한다. 이 목록은 정적 검사에서 "봤고, 분류했고, 근거가 있다"를
# 남기는 자리이지 면제 도장이 아니다.
#
# ## 형식
#
#   <검사 대상 루트 기준 상대 경로><TAB><금지 문자열><TAB><근거>
#
# 경로는 정확히 일치하거나, `*`가 들어 있으면 셸 글롭으로 본다. 경로를 반드시
# 적게 한 이유는 전역 면제를 막기 위해서다 — 같은 문자열이 **다른 파일**에
# 나타나면 그것은 여전히 위반이다. bundle/pg처럼 상대 경로가 다른 검사
# 대상에는 이 목록의 어떤 줄도 걸리지 않는다.
#
# 예외가 하나 있다. `…/__pycache__/X.cpython-312.pyc`는 `…/X.py`의 규칙을
# 따른다 — .pyc의 문자열 상수는 그 .py를 컴파일한 결과라 같은 문자열이고 같은
# 근거다. 이 매핑이 없으면 번들 python을 실행한 뒤와 전에 검사 결과가 달라져
# **검사 순서에 따라 답이 바뀌는** 검사기가 된다.
#
# 이 파일과 forbidden-strings.txt 둘만 검사기가 자기 검사 대상에서 제외한다
# (패턴 원본이라 자기에게 걸린다).
