## 목표와 전제

앱 아이콘 하나로 담화를 실행하고, DB·API·worker·embed의 시작과 종료를 앱이 관리한다. 최종적으로 Python·uv·Homebrew·Docker를 별도로 설치하지 않아도 사용하는 macOS 앱을 제공한다.

- 첫 지원 대상은 Apple Silicon 맥으로 가정한다. 최소 macOS 버전은 Phase 0에서 결정한다.
- 기존 React·NestJS·Python·PostgreSQL 구조와 로컬 처리 원칙을 유지한다.
- 최초 배포 방식은 DMG 직접 배포로 가정한다.
- Intel 맥 지원, Mac App Store 출시, SQLite 전환은 이번 범위에서 제외한다.
- AI 모델은 최초 실행 시 필요한 모델을 다운로드하고 재사용하는 방식을 기본 방향으로 둔다. 모델별 이용 동의와 토큰 요구사항은 별도로 처리한다.

위 지원·배포 전제는 상세 스펙 작성 시 확정한다. 현재 라이브러리 조합의 독립 패키징 성공을 검증한 상태는 아니며, Phase 0 결과에 따라 후속 범위를 조정한다.

## 최종 구성

하나의 `Damwha.app`에 실행 환경을 포함하되, 내부에서는 여러 프로세스로 실행한다.

| 앱 패키지에 포함 | 앱 외부의 전용 데이터 폴더에 저장 |
| --- | --- |
| Electron 및 React 화면 | 설정과 로그 |
| NestJS API 실행 환경 | 녹음 파일 및 처리 결과 파일 |
| PostgreSQL 실행 파일 및 pgvector·pg_bigm 확장 | 실제 PostgreSQL 데이터 |
| Python 및 ML 라이브러리, worker·embed 코드 | 다운로드한 AI 모델 및 캐시 |
| ffmpeg 실행 파일 | 백업 및 데이터 이전 작업 파일 |

사용자 데이터의 기본 위치는 `~/Library/Application Support/Damwha/`를 후보로 둔다. 앱 교체·업데이트와 데이터 수명을 분리하며, 정확한 하위 경로는 초기 스펙에서 확정한다.

## Phase 구성

### Phase 0. 패키징 기술 검증

**목표:** 완전한 설치형 앱의 핵심 기술 위험을 먼저 확인한다.

범위:

- macOS용 PostgreSQL과 pgvector·pg_bigm의 독립 실행 검증.
- Python 및 현재 PyTorch·MLX 등 ML 라이브러리 조합의 재배치·독립 실행 검증.
- ffmpeg 실행과 필요한 네이티브 라이브러리 의존성 확인.
- 포함 바이너리의 서명 제약, 모델 배포·이용 조건 확인.
- 지원 macOS 버전, 실행 환경 제공 방식, 대략적인 설치 용량과 초기 준비 비용 결정.

- 가능한 패키징 방식, 검증 환경, 남은 제약을 문서로 기록.
- 후속 Phase에서 사용할 실행 환경 제공 방식을 결정. 실패한 항목은 대안 검증 후 진행.

### Phase 1. Electron 앱 기반

**목표:** 기존 담화를 맥 앱 창에서 사용한다.

범위:

- 모노레포에 데스크톱 패키지 추가 및 기존 React 화면 연결.
- NestJS API 실행과 화면 준비 상태 연결.
- 앱 중복 실행 방지, 로컬 통신 경계, 마이크 권한 처리.
- 실행 파일·사용자 데이터 경로와 서비스 실행 계약의 기반 정의.
- 앱이 만든 자식 프로세스(API 하나)의 종료 정리. **자기가 만든 프로세스의 정리는 그것을 만든 Phase가 진다** — Phase 2의 "정상 종료와 자식 프로세스 정리"는 이 단일 절차를 DB·worker·embed까지 확장하는 일이다.

완료 기준:

- 앱 아이콘으로 실행하여 업로드·녹음·검색 가능.
- DB와 worker·embed는 기존 환경에서 실행해 사용.
- 기존 웹 개발·실행 흐름과 충돌하지 않음.

**상태 (2026-09-11): 구현 12개 Task 완료, 통합 검증 완료, 수정 3회차 완료. 완료 기준 3개 전부 충족.**

### Phase 2. 서비스 실행 통합

**목표:** 터미널에서 서비스를 각각 실행하는 불편을 제거한다.

범위:

- 기존 설치 환경을 활용한 DB 준비 확인·기동 연계 및 worker·embed 자동 실행.
- 의존성에 따른 시작 순서, 준비 상태 확인, 실패 표시, 재시작과 로그 관리.
- 정상 종료와 자식 프로세스 정리 — Phase 1이 API 하나에 대해 세운 절차를 전체 서비스로 확장하고, 의존 역순 종료를 정의한다.
- 창 닫기와 앱 종료 구분, 녹음·분석 중 종료 동작 정의.
- 기존 실행 파일을 후속 Phase의 내장 실행 파일로 교체할 수 있는 계약 확정.

완료 기준:

- 사전 설치 환경이 갖춰진 현재 맥에서 앱 실행만으로 전체 서비스 준비.
- 앱이 생성한 자식 프로세스가 종료 후 남지 않음 — 전체 서비스 기준. API 하나에 대한 같은 기준은 Phase 1이 이미 통과한 상태다.
- 외부에서 이미 실행 중인 서비스를 앱 소유 프로세스와 구분하여 관리.
- 서비스 시작 실패 시 원인과 복구 방법을 앱에서 확인 가능.

이 단계까지는 기존 DB·Python 설치가 필요하다. 현재 사용자의 실행 불편을 해결하는 첫 실사용 목표다.

**Phase 3~6으로 넘기는 완료 기준은 없다.** 결과 문서 §5에 남긴 것은 동작·안내 수준의 한계다 —
(1) 게이트 실패 뒤 창이 상한 없이 20초마다 자동 재시도한다(Phase 3의 마이그레이션 실행 게이트와 함께
정리), (2) `UV_BIN`·`DOCKER_BIN`을 고친 뒤 "다시 시도"로는 반영되지 않고 앱을 다시 켜야 한다,
(3) 종료 화면이 긴 마무리 동안 진행 표시가 없다, (4) worker supervisor가 **크래시**해 재시작되면 이전
`--once` 자식을 추적하지 않는다 — job lease token과 함께 Phase 6이 받는다. Phase 1에서 넘어온
`unverified-owner` 종단간 발화와 TCC 재요청(R1-6)은 이번 검증에서도 기회가 없어 미확인이다.

### Phase 4. Python·ML 실행 환경 내장

### Phase 6. 배포·업데이트

**목표:** 다른 맥에서도 설치하고 업데이트할 수 있게 한다.

범위:

- 재현 가능한 빌드와 버전 관리.
- 앱 및 포함 바이너리 서명·공증, DMG 생성.

완료 기준:

- 개발 환경이 없는 지원 대상 맥에 배포 산출물을 설치하고 실제 처리 성공.
- 이전 버전에서 업데이트해도 회의 기록과 설정 유지.

서명 관련 위험 검증은 Phase 0부터 진행하며, 배포 검증을 이 단계에서 완성한다.

## 진행 순서와 중간 목표

기본 순서는 Phase 0 → 1 → 2 → 3 → 4 → 5 → 6이다.

- **Phase 2:** 현재 맥에서 앱 하나로 전체 서비스 실행.
- **Phase 4:** 개발 도구 없이 실행 가능한 설치형 구성 확보.
- **Phase 6:** 다른 사용자에게 배포하고 업데이트 가능한 앱 확보.

Phase 3과 4는 기술적으로 분리 가능한 부분이 있지만, 실행·경로 계약을 Phase 1~2에서 먼저 고정한다. 실제 병렬 진행 여부는 각 구현 계획에서 판단한다.

## Phase별 문서와 실행 방식

전체 범위는 이 로드맵에서 관리하고, 상세 스펙과 계획은 각 Phase 착수 직전에 작성한다. Phase 0의 결과를 확인하기 전에 후속 패키징 방식을 모두 확정하지 않는다.

모든 Phase는 **구현 스펙 → 스펙 리뷰 → 구현 계획 → 계획 검증 → 계획 실행(단계별 리뷰 필수) → 결과 반영** 순서로 진행한다. Phase 0도 같은 흐름을 따르되, 구현 대상은 기술 검증 실험이고 최종 결과는 검증 보고서와 기술 결정이다.

### 1. 구현 스펙

- 목표와 포함·제외 범위, 선행 Phase에서 인계받는 조건을 명시한다.
- 사용자 동작, 구성요소 간 계약, 데이터·프로세스 소유권, 실패·복구 동작을 정의한다.
- 완료 기준에 식별자를 붙이고, 각 기준을 어떤 환경에서 어떻게 확인할지 적는다.
- 미확정 사항과 기술 위험을 구분한다. 구현에 영향을 주는 미확정 사항은 리뷰 통과 전에 해결하거나 별도 검증 단계로 명시한다.

### 2. 스펙 리뷰

- Phase 목표와 범위가 로드맵에 부합하는지, 기존 코드·계약과 충돌하지 않는지 확인한다.
- 정상 동작뿐 아니라 시작 실패·중단·재시작·데이터 보존 조건을 검토한다.
- 완료 기준이 관찰·검증 가능한지, 요구사항 간 모순이나 누락이 없는지 확인한다.
- 지적 사항, 수정 내용, 재검토 결과를 기록한다. 범위·계약·데이터 안전성·완료 기준에 영향을 주는 지적이 남아 있으면 구현 계획으로 넘어가지 않는다.
- 리뷰를 통과한 스펙에 대해 사용자가 범위와 주요 동작을 승인한 뒤 구현 계획을 작성한다.

### 3. 구현 계획

- 작업을 각각 구현·검증·리뷰 가능한 크기의 단계로 나눈다.
- 각 단계에 목표, 변경 파일·모듈, 선행 조건, 작업 내용, 관련 스펙 완료 기준을 적는다.
- 각 단계의 검증 명령 또는 수동 검증 절차, 기대 결과, 리뷰 항목을 정의한다.
- 마지막 단계에는 Phase 전체 통합 검증과 결과 기록을 포함한다.
- 위험한 변경에는 실패 시 복구 방법을 포함한다. 아직 실행하지 않은 검증을 성공으로 가정하지 않는다.

### 4. 계획 검증

- 모든 스펙 완료 기준이 구현 단계와 검증 절차에 연결되어 있는지 확인한다.
- 단계 순서·의존성, 파일 경로·명령, 필요한 도구·실행 환경이 실제 저장소와 맞는지 확인한다.
- 각 단계가 개별 리뷰 가능한지, 데이터 변경·프로세스 종료·실패 복구가 빠지지 않았는지 확인한다.
- 계획에 스펙 밖의 작업이 들어가거나 스펙 변경이 필요해졌다면 스펙 리뷰로 돌아간다.
- 지적 사항을 수정하고 재검증한 뒤 계획을 실행 가능한 상태로 확정한다. 구현 중의 테스트·통합 검증을 이 사전 검증으로 대체하지 않는다.

### 5. 계획 실행 — 단계별 리뷰 필수

계획 내부의 각 단계는 다음 순서를 반복한다.

1. 해당 단계 구현.
2. 계획에 명시한 테스트·실행 검증 수행 및 증거 기록.
3. 변경 사항을 스펙·계획·기존 동작과 대조하여 리뷰.
4. 지적 사항 수정 후 관련 검증과 리뷰 재수행.
5. 단계 완료 기록 후 다음 단계 진행.

- **단계별 리뷰를 생략하거나 여러 단계가 끝난 뒤 한 번의 최종 리뷰로 대체하지 않는다.**
- 리뷰는 구현 직후의 완료 선언과 구분된 검토 절차로 수행한다. 검토자와 검토 대상 커밋 또는 diff를 기록한다.
- 기능 오류, 계약 위반, 데이터 손실 가능성, 필수 검증 실패·누락은 다음 단계 진행을 막는다. 범위 밖의 개선 제안은 이유와 후속 작업을 남겨 분리할 수 있다.
- 단계별 리뷰는 매번 사용자의 수동 승인을 요구한다는 의미는 아니다. 승인된 범위 안의 수정은 계속 진행하고, 범위나 주요 동작이 바뀌면 스펙을 갱신·재리뷰하고 사용자에게 확인한다.
- 모든 단계 완료 후 Phase 전체 완료 기준과 통합 동작을 검증하고 최종 리뷰한다.

### 6. 결과 반영

- 완료한 범위, 검증 환경·명령·결과, 리뷰 지적과 해결 여부를 결과 문서에 기록한다.
- 남은 제약, 후속 Phase에 넘길 작업, 기술 결정과 변경 이유를 정리한다.
- 로드맵의 진행 상태와 관련 패키지의 운영 문서를 실제 구현에 맞게 갱신한다.
- 완료 기준을 충족하지 못하면 해당 Phase를 미완료로 유지한다. 범위 변경으로 해결하려면 변경 내용을 명시하고 스펙 리뷰를 다시 거친다.
- 결과 문서와 최종 diff 리뷰까지 통과한 뒤 Phase 브랜치를 병합한다.

문서 위치:

- 전체 로드맵: `docs/electron-migration-roadmap.md`
- Phase별 스펙: `docs/superpowers/specs/YYYY-MM-DD-electron-phase-N-<topic>-design.md`
- Phase별 계획: `docs/superpowers/plans/YYYY-MM-DD-electron-phase-N-<topic>.md`
- Phase별 리뷰·실행 결과: `docs/superpowers/reports/YYYY-MM-DD-electron-phase-N-<topic>-results.md`

결과 문서에는 스펙 리뷰, 계획 검증, 단계별 실행·리뷰, 최종 검증을 구분해서 기록한다. 각 기록에는 대상 버전 또는 커밋, 검토자, 지적 사항, 조치, 검증 증거, 통과 여부를 포함한다.

작성·리뷰 중인 문서는 수정할 수 있다. 확정된 날짜별 스펙·계획은 당시 결정의 기록으로 보존하고, 확정 후 설계 변경은 후속 문서에 원문 링크와 변경 이유를 남긴다. 진행 상태와 변경된 전체 범위는 이 로드맵에 반영한다.

## 사용하는 스킬 — superpowers 플러그인

**위 여섯 단계는 `superpowers` 플러그인의 스킬로 진행한다.** 전용 하네스를 따로 만들지 않는다.

| 단계 | 스킬 |
| --- | --- |
| 1. 구현 스펙 | `superpowers:brainstorming` — 스펙을 쓰기 전에 의도·요구사항·설계를 먼저 좁힌다 |
| 3. 구현 계획 | `superpowers:writing-plans` |
| 5. 계획 실행 | `superpowers:executing-plans`(별도 세션에서 리뷰 체크포인트를 두고 실행) 또는 단계가 서로 독립적이면 `superpowers:subagent-driven-development`(현 세션에서 Task를 서브 에이전트로) |
| 5. 단계별 리뷰 | `superpowers:requesting-code-review` / `superpowers:receiving-code-review` |
| 5·6. 완료 선언 전 | `superpowers:verification-before-completion` — 증거 없이 "통과"라고 쓰지 않는다 |
| 구현 중 | `superpowers:test-driven-development`, 버그·검증 실패에는 `superpowers:systematic-debugging` |
| 브랜치 운영 | 병합 판단에 `superpowers:finishing-a-development-branch` |

스킬이 대체하지 않는 이 로드맵의 규칙은 그대로 적용한다.

- 리뷰어는 구현 대화를 받지 않고 **diff·스펙·계획·검증 증거만으로** 판단한다.
- 한 단계의 수정 루프는 **3회를 넘기지 않는다.** 넘어가면 계획 자체의 결함을 의심하고 사용자에게 확인한다.
- **스펙·스펙 리뷰·계획 검증(1·2·4단계)은 메인 세션이 진행한다.** 이 세 단계는 사용자 승인이 걸려 있어 서브 에이전트에 넘기지 않는다.
- 계획의 각 단계는 `Verify`와 `Review` 블록을 갖추고, 4단계(계획 검증)가 그 형식을 확인한다.

**Phase 0은 이 방식이 아니었다.** 전용 스킬 `electron-plan-execute`와 서브 에이전트 `electron-implementer`·`electron-verifier`·`electron-reviewer`로 진행했고, Phase 0 결과 문서의 "검토자 (model)" 열이 그 에이전트 이름을 가리킨다. **그 넷은 지웠다** — 위 표로 대체되어 더 쓰지 않는다. 당시 정의를 봐야 하면 커밋 `1175212`(`chore: Electron 전환 계획 실행용 개발 하네스를 추가한다`)나 태그 `archive/electron-phase-0-packaging-validation`에 있다.

## 브랜치 운영 방식

**Phase별 브랜치를 만들고 순차적으로 병합한다. 전체 전환을 하나의 장기 브랜치에서 진행하지 않는다.** Phase별 변경 범위와 리뷰·복구 단위를 일치시키고, 앞 단계에서 검증된 결과를 다음 단계의 기준으로 사용하기 위한 결정이다.

- Phase 착수 시 저장소의 실제 기본 브랜치를 확인하고 최신 상태에서 `feat/electron-migration-phase-N-<topic>` 브랜치를 만든다.
- 해당 Phase의 스펙·계획·구현·리뷰 결과를 같은 브랜치에서 관리한다. Phase 0도 검증 문서와 필요한 실험 코드를 별도 브랜치에서 관리하되, 일회성 산출물은 제품 코드에 포함하지 않는다.
- 계획 내부 단계마다 브랜치를 추가하지 않는다. 리뷰 가능한 커밋으로 나누고 결과 문서에서 단계와 커밋을 연결한다.
- 기본적으로 Phase당 PR 하나를 사용한다. 작업 중 초안 PR을 열 수 있으며, 단계별 리뷰와 최종 검증을 통과한 뒤 병합한다.
- 이전 Phase가 기본 브랜치에 병합된 후, 갱신된 기본 브랜치에서 다음 Phase 브랜치를 만든다. 병합 전의 Phase 브랜치 위에 다음 Phase를 연쇄로 쌓지 않는다.
- 작업 디렉터리는 기본 저장소 하나를 쓴다. Phase 브랜치를 만들고 그 자리에서 작업한다. 별도 worktree를 두지 않는다 — Phase 1~2는 기존 서비스 코드를 고치지 않고 데스크톱 패키지를 더하는 범위라 병행할 작업이 없다. 한 저장소에서 두 브랜치를 동시에 열어야 할 일이 실제로 생기면 그때 worktree를 만든다.
- Phase가 너무 커서 리뷰하기 어렵다면 구현 전에 범위를 `3a`, `3b`처럼 하위 Phase로 나누고 로드맵·스펙·병합 순서를 갱신한다.
- 병렬 작업은 공통 계약이 확정되고 독립성이 확인된 경우에만 별도 계획으로 정한다. 각 브랜치는 병합 전 최신 기본 브랜치를 반영하고 통합 검증한다.

Phase 완료와 병합은 배포를 의미하지 않는다. 사용자에게 배포할 설치 파일의 준비·검증은 Phase 6의 기준을 따른다. 이 문서 정리만으로 실제 Phase 브랜치를 생성하거나 구현을 시작하지 않는다.

## 공통 설계 원칙

- 실행 파일은 앱 내부, 변경 가능한 데이터는 앱 외부에 둔다.
- DB를 먼저 준비하고 의존 서비스의 준비 상태를 확인한 뒤 사용 가능한 상태를 표시한다.
- 개발 환경과 내장 환경이 동일한 서비스 실행 계약을 사용하게 한다.
- 앱이 생성한 프로세스와 기존 외부 서비스를 구분한다.
- API와 worker의 PostgreSQL 작업 큐 계약 및 기존 데이터 보호 규칙을 유지한다.
- 단순 앱 재실행 검증과 실제 다른 맥에서의 독립 설치 검증을 구분한다.
- DB 런타임의 메이저 버전 업그레이드와 일반 SQL 스키마 마이그레이션을 구분해 계획한다.
