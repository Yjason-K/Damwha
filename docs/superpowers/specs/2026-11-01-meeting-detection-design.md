**작성일:** 2026-11-01
**선행:** `origin/main` @ `b493f11` (시스템 오디오 PR #67 포함). 브랜치 `feat/meeting-detection`.
`dev`(`3eb4fa9`)에는 시스템 오디오가 없어 사용자가 말한 `dev` 대신 `main`에서 땄다. `dev`는 `main`보다 10커밋 뒤이고
앞선 커밋은 없다.
**대체:** 없음. 새 기능이다. `2026-10-26-system-audio-capture-design.md`가 예고한 후속이다. Phase 2 스펙 §6.11
("렌더러 → main 경로를 만들지 않는다")은 그대로 지킨다(§4.3).
**범위:** desktop의 감시 헬퍼·감지 흐름·카드 창·메뉴·빌드·서명·번들 검사, fe의 데스크톱 다리와 녹음 시작 공용화.
be·worker·`@damwha/contracts`·DB 변경 없음.

## 1. 목표

Zoom이나 Google Meet을 쓰려는 순간 화면 위쪽 가운데에 카드가 떠서, 버튼 하나로 녹음을 시작한다. 회의가 끝나면 녹음이
저절로 멈추고 요약까지 이어진다. 노션 AI 회의록의 "AI 노트 시작하기"가 원형이다(사용자가 스크린샷으로 지목).

**왜:** 회의 시작 전에 담화를 열어 녹음을 거는 일을 잊으면 그 회의는 남지 않는다. 담화가 먼저 물어보면 잊을 일이 줄어든다.

### 목표

- 정해둔 앱(Zoom, Teams, Chrome)이 마이크를 쓰기 시작하면 카드를 띄운다.
- 카드의 `녹음 시작` 한 번으로 마이크와 시스템 오디오를 녹음한다.
- 그 앱의 마이크 사용이 끝나면 자동으로 멈추고 전사·요약으로 이어진다.

### 비목표

- 사용자 확인 없는 자동 녹음. 카드를 누르지 않으면 마이크를 열지 않는다.
- 캘린더 연동, 참석자 동의 안내(담화는 개인용이고 녹음 고지를 하지 않는다, `fe/CLAUDE.md`).
- Safari 등 목록 밖 앱, Chrome 탭 판별, 앱별 끄기, Windows.

### 안티 목표 (동작해도 실패다)

- 다른 앱의 통화·소리·키보드 입력에 영향을 준다.
- 카드가 포커스를 뺏어 입력 중인 글자가 끊긴다.
- 음소거를 회의 종료로 착각해 회의 도중 녹음이 멈춘다.
- 담화가 켠 마이크를 다시 감지해 카드를 띄운다.

## 2. 실측 (2026-11-01, macOS 27.2, 터미널에서 돌린 Swift 프로브)

| 확인 | 결과 |
| --- | --- |
| `kAudioHardwarePropertyProcessObjectList` + `kAudioProcessPropertyIsRunningInput`·`...Output`·`...BundleID`·`...PID` | 동작. 프로세스별로 입력·출력 여부와 번들 ID가 나온다. 권한 창 없음 |
| Meet 입장 | `com.google.Chrome.helper` 입력·출력 켜짐 |
| Meet 음소거·해제 (사용자가 수행) | 입력이 끊기지 않음 (2분 17초 연속) |
| Meet 빨간 버튼 (탭 유지) | 입력이 즉시 꺼지고 1초 뒤 출력도 꺼짐 |

처음 조사한 `kAudioDevicePropertyDeviceIsRunningSomewhere`는 쓰지 않는다. 앱을 구분하지 못해, 담화가 녹음 중이면 회의가
끝나도 켜진 채로 남는다.

**실측 안 된 것:** Zoom, Teams, 서명된 패키지에서의 동작, 입장 전 미리보기 화면에서의 입력 여부. 구현 첫 단계(§7 T0)에서 본다.

앱 최소 버전이 macOS 15.0이라 이 API(14.2+)의 하한 문제는 없다.

## 3. 사용자 흐름

1. 담화 앱이 켜져 있고 화면이 API에 붙어 있으며 녹음 중이 아니다.
2. 대상 앱의 입력이 **2초** 이상 이어지면 카드를 띄운다. 음성 검색 같은 찰나의 사용을 거른다.
3. 카드 문구: `회의를 기록할까요?` / `녹음은 이 Mac에만 저장돼요`. 버튼은 `녹음 시작`, `닫기`. (시안 B2)
4. **30초** 동안 응답이 없으면 카드는 사라진다. `닫기`와 같게 취급한다.
5. `닫기` 또는 무시: 그 앱의 입력이 **60초** 연속으로 꺼지기 전까지 다시 띄우지 않는다(억제). **녹음이 끝난 뒤와 시작 실패 뒤에도**, 어떤
   방식으로 시작한 녹음이든 같은 억제를 건다. 없으면 회의가 이어지는 동안 카드가 반복해서 뜬다. 녹음을 직접 멈춘 뒤 같은 회의를 다시
   녹음하려면 모달을 쓴다.
6. `녹음 시작`: 카드가 작은 녹음 표시(`녹음 중`, `중지`)로 바뀐다. 담화 창을 앞으로 띄우지 않고, 현재 화면도 옮기지 않는다.
7. 그 앱의 입력이 **10초** 연속 꺼지면 멈춘다. 그 안에 돌아오면 계속 녹음한다.
8. 멈춘 뒤 `녹음을 마쳤어요`와 `회의 보기`를 **10초** 보여준다. `회의 보기`는 담화 창을 앞으로 띄우고 그 회의로 이동한다.

시간 값은 첫 구현의 기본값이고, 실사용으로 조정한다.

- **자동 종료는 카드로 시작한 녹음에만** 건다. 모달로 시작한 녹음은 지금처럼 사용자가 멈춘다.
- **녹음 중에는** 어떤 방식으로 시작했든 카드를 띄우지 않는다.
- **자동 종료가 안 맞는 앱:** T0에서 음소거로 입력이 꺼지는 앱은 목록에 `autoStop: false`로 두고, 카드로 시작만 한다. 녹음 표시의
  `중지`로 멈춘다.
- **시스템 오디오:** 카드 시작은 모달의 저장된 선택(`damwha:live-system-audio`)과 무관하게 **항상 켠다**. 회의 상대 목소리가
  빠지면 이 기능의 의미가 없다.
- **제목·처리 설정:** 제목은 비워 기존 규칙(브라우저 시각)을 쓴다. 전역 처리 설정을 쓰고, `defer_lens`·`defer_summary`는 보내지 않아
  요약과 렌즈가 자동으로 돈다.
- **권한 거절·장치 실패:** 준비가 실패하면 회의를 만들지 않고(기존 규칙) 카드에 `녹음을 시작하지 못했어요`를 보여주고 닫는다.

## 4. 구조

```
mic-watch 헬퍼 ──JSON 줄──> process/mic-watch.ts ──> app/meeting-detection.ts (상태 기계)
                                                         │              │
                                       executeJavaScript │              │ 표시·갱신, next() 묻기
                                                         v              v
                                        fe desktop-bridge        카드 창 (shell/detect.html)
```

### 4.1 감시 헬퍼 (새 Swift 바이너리)

`desktop/native/mic-watch/main.swift`. 마이크를 열지 않고 오디오를 받지 않으며 상태만 읽는다. 1초마다 프로세스 목록을 읽어, 입력을
쓰는 번들 ID 집합이 바뀌었을 때만 stdout에 JSON 한 줄을 쓴다.

```json
{"input":["com.google.Chrome.helper"]}
```

기동 직후에는 빈 집합이어도 **전체 스냅숏을 반드시 한 줄** 쓴다. 조회가 실패하면 빈 집합이 아니라 `{"error":"<단계> <OSStatus>"}`를 쓴다.
stdin EOF·SIGTERM에 끝난다(시스템 오디오 헬퍼와 같은 계약). 프로세스 목록의 변경 리스너로 깨우는 방식은 도입하지 않는다. 폴링이면
충분하고, 상태 변화가 1초 안에 잡히는 것으로 실측의 판단이 성립한다. 대상 앱 판별은 main이 한다(헬퍼는 목록을 모른다).

**담화 제외는 목록으로 된다.** 담화의 번들 ID는 대상 목록에 없으므로 자기 녹음을 감지하지 않는다.

빌드·서명은 `damwha-system-audio`와 같은 길을 탄다(`build-system-audio.sh`, `package.mjs`의 runtime 서명, `check-bundle` 항목 추가).
스테이징 자리를 공유할지 나눌지는 구현에 맡긴다.

### 4.2 상태 기계 (`desktop/src/app/meeting-detection.ts`)

electron을 import하지 않는 순수 모듈이다(`main.ts`는 vitest가 못 부른다). 시계·헬퍼 이벤트·잎 동작을 주입받는다.

상태: `idle` → `prompting` → `recording` → `finished` → `idle`, 그리고 앱별 억제(`닫기` 뒤 §3-5).

대상 목록은 코드 상수 하나다.

```ts
{ name: "Chrome", bundlePrefix: "com.google.Chrome", autoStop: true }
```

Zoom·Teams 항목과 번들 ID는 T0 실측값으로 채운다. 접두사 일치로 helper 프로세스까지 잡는다.

**감시 상태는 `정상`/`불명` 둘이다.** 헬퍼 종료·`error` 줄·기동 직후 첫 스냅숏 전은 `불명`이다. `불명`을 "입력 없음"으로 읽지 않는다:
새 카드를 띄우지 않고, 진행 중인 10초 종료 카운트다운을 취소한다. 지수 백오프로 재시작해 전체 스냅숏을 받은 뒤에만 판단을 재개한다.
`supervisor.log`에 남기고 화면에는 알리지 않는다. 녹음은 멈추지 않고, 복구되지 않으면 `중지`로 끝낸다.

**대상 앱은 카드를 띄울 때 하나로 고정한다.** 동시에 여럿이면 목록 앞쪽이 대상이다. 카드 표시·녹음 중에는 다른 앱의 입력으로 새 카드를 띄우지 않는다.
자동 종료는 `autoStop: true`인 대상에서만 시작하고, **목록의 모든 앱 입력이 꺼졌을 때** 10초를 잰다. 잘못 멈추는 것이 안 멈추는 것보다 나쁘다.
억제(§3-5)는 대상 앱에만 건다.

**종료와의 순서.** 앱 종료·창 닫기 흐름이 시작되면 상태 기계를 멈춘다: 새 감지·시작을 받지 않고 카드를 닫는다. 렌더러 호출은 전부 상한을 두고
(`recording-bridge.ts`), 응답에 카드 세대를 맞춰 낡은 응답이 새 상태를 덮지 못하게 한다. 시작 호출이 상한을 넘으면 카드에 시작 실패를 보여준다.

### 4.3 카드 창

- `shell/detect.html`을 담는 frameless `BrowserWindow`. preload 없음, 셸과 같은 webPreferences, 항상 위, 모든 Space에 표시. 화면 위쪽
  가운데에 작은 크기로 둔다. 셸 페이지 규칙(토큰 동기화, CSP, macOS 다크 추종, `tests/windows/shell-html.test.ts`)을 따른다.
- **나타날 때 포커스를 뺏지 않는다.** `type: "panel"` + `showInactive()`를 쓴다. 사용자가 카드를 **클릭할 때** 포커스가 옮겨 가는 것은
  허용한다. 입력을 멈추고 직접 누른 것이라 안티 목표에 걸리지 않는다.
- **버튼 경로:** 상태 창의 "서비스 다시 시작"과 같은 방식이다. main이 카드 페이지의 `next()`를 `executeJavaScript`로 걸어 두고, 버튼을
  누르면 그 호출이 `start`·`dismiss`·`stop`·`open` 중 하나를 답으로 돌려준다(`status-window.ts`의 `SERVICES_ASK_SCRIPT` 패턴). preload·IPC·
  새 스킴이 없고 `shell-html.test.ts`의 탐색 금지에도 걸리지 않는다.
- 화면 공유 노출: `setContentProtection(true)`를 건다. 최신 macOS의 ScreenCaptureKit이 이를 무시한다는 보고가 있어 실제로 가려지는지 본다.
  가려지지 않아도 막지 않고 알려진 한계로 기록한다.

### 4.4 fe 다리 (`fe/src/features/meeting/lib/desktop-bridge.ts`)

기존처럼 main → 렌더러 한 방향이다. 이름은 main.ts에 문자열로 적히므로 바꾸면 조용히 끊긴다.

- `startDetectedRecording(): Promise<{ started: boolean; meetingId?: string; reason?: string }>`
- `recordingStatus()`: 아래 타입을 돌려준다.

  ```ts
  {
    phase: "idle" | "starting" | "recording" | "stopping" | "ended";
    meetingId: string | null;
    failed: boolean;            // 실패가 기록됐고 서버 마감이 아직 필요할 수 있다
    systemAudioLost: boolean;
    end: "acked" | "discarded" | "sealed" | "failed" | null;  // 세션의 종결 결과
  }
  ```

- `finishRecording(): Promise<void>`, 실패로 이미 `stopped`에 수렴한 세션도 `recorder.stop()`까지 부른다.
- `openMeeting(id: string): void`, 라우터로 이동한다.

기존 `stopLiveRecording()`을 자동 종료와 `중지`에 그대로 쓴다. 종료 경로를 새로 만들지 않는다.

**레코더 실패에는 쓸 수 없다.** 실패한 레코더는 `stopped`로 수렴해 `hasLiveCapture()`가 거짓이고, `stopLiveRecording()`은 `no-recording` 성공을
돌려줄 뿐 서버 stop을 보내지 않는다. 그래서 `finishRecording()`을 따로 둔다. `recorder.stop()`은 중복 호출에 같은 Promise를 돌려주므로 안전하다.

**종결 결과는 `live-session.ts`가 세션별로 보관한다.** `recording: false`나 `stopped: true`는 성공의 증거가 아니다 — `sendStop()`이 거절돼도 phase는
`stopped`가 되고 회의는 서버에 `recording`으로 남는다. 또 화면의 종료는 `clearLiveCapture`로 `active`를 지우므로, 마지막 종결 결과를 `active`와 별도로
둬야 main이 읽을 수 있다. 어떤 종료 경로든 같은 자리에 쓴다.

**시작 중을 상태로 둔다.** 준비와 `POST /meetings/live` 사이에는 `meetingId`가 없어 `hasLiveCapture()`가 거짓이다. `startDetectedRecording`은:
- `active`가 있으면(모달이 준비 중이어도) 시작하지 않고 `{ started: false, reason: "busy" }`를 돌려준다.
- 진행 중 Promise를 모듈에 둔다. 그동안 `isRecording()`은 참이고, `stopLiveRecording()`은 그 Promise를 기다린 뒤 멈춘다. 그래서 창 닫기·앱 종료의 기존
  확인과 handshake가 시작 중에도 동작한다.
- 모달의 시작도 카드가 시작 중이면 busy로 막는다. 공용 시작 함수 안에서 한 번만 검사한다.

`new-meeting-dialog.tsx`의 시작 흐름(`prepareLiveRecorder` → `POST /meetings/live` → `beginLiveCapture`)을 공용 함수로 꺼내 모달과 다리가
같이 쓴다. "캡처를 먼저 준비하고, 성공한 뒤에야 회의를 만든다" 순서를 두 벌로 만들지 않는다.

main은 `recording` 상태에서 **2초**마다 `recordingStatus()`를 물어(기존 `recording-bridge.ts`의 상한 패턴) 수동 종료·실패·4시간 봉인을 안다.
끝난 방식에 따라 갈린다(§4.7).

담화 창은 앞으로 올리지 않는다. 렌더러의 사용자 제스처 제약은 `executeJavaScript(code, true)`로 풀고, 부족하면 메인 창의
`webPreferences.autoplayPolicy`로 푼다. 실제로 `AudioContext`가 시작되는지 T0에서 확인한다. **둘 다 안 되면 구현을 멈추고 사용자와 다시
정한다** — 창을 올리거나 캡처를 main 쪽으로 옮기는 안이 있지만, 지금 정하지 않는다.

### 4.5 켜고 끄기

기본은 켬이다. 담화 메뉴의 체크 항목 `회의 감지`로 끈다. 값은 `<userData>/detection-state.json`에 둔다(`update-state.json`과 같은 형태).
꺼지면 헬퍼를 끈다. fe 설정 화면에 두지 않는 이유는 렌더러 → main 경로가 또 필요해서다.

### 4.6 창이 없을 때

macOS에서 창을 닫아도 앱은 살아 있다. 메인 창이 없거나 화면이 API에 붙어 있지 않으면 카드를 띄우지 않는다. 녹음은 렌더러에 사는데, 창을
새로 만들며 시작하는 경로는 실패 면이 넓다. 이 경우를 푸는 것은 후속이다.

녹음 중 창을 닫는 경우는 기존 창 닫기 흐름(확인 대화상자)을 그대로 탄다.

### 4.7 끝나는 방식별 처리

끝났다고 말할 때 없는 녹음을 있다고 하지 않는다.

| 상황 | 알아채는 법 | main의 동작 | 카드 |
| --- | --- | --- | --- |
| 정상 종료 (자동·`중지`·앱 밖 수동) | `end: "acked"` | 없음 | `녹음을 마쳤어요` + `회의 보기` |
| 4시간 봉인 | `end: "sealed"` | 없음 | 위와 같음 |
| 레코더 실패 (`device_ended`·`upload_failed` 등) | `failed: true`, `end: null` | `finishRecording()`을 불러 마감한다. 배너를 보는 사람이 없어 아니면 회의가 `recording`에 남는다 | `녹음이 중단됐어요` / `지금까지 녹음된 내용은 남아 있어요` + `회의 보기` |
| 서버가 stop을 거절 | `end: "failed"` | 없음 (orphan 스위퍼가 닫는다) | 위와 같음 |
| 0바이트 등으로 회의 폐기 | `end: "discarded"` | 없음 | `녹음된 내용이 없어요`, 버튼 없음 |
| 렌더러 리셋 (⌘R, 크래시) | `meetingId`가 사라짐, 또는 응답 없음이 상한 안에서 반복 | 없음 (orphan 스위퍼가 닫는다) | `녹음이 끊겼어요` / `담화에서 회의를 확인해 주세요`, 버튼 없음 |

녹음 중 `systemAudioLost`가 참이면 녹음 표시를 `마이크만 녹음 중`으로 바꾼다. 기존 토스트는 뒤에 있는 담화 화면에만 떠서 사용자가 못 본다.

## 5. 다른 서비스에 대한 영향

- **감지:** 상태만 읽고 마이크를 열지 않는다(실측, 권한 창 없음).
- **녹음:** 사용자가 눌러야 시작한다. macOS는 입력 장치를 앱끼리 공유하고, 시스템 오디오는 Process Tap으로 복사해 받는다(기존 기능).
- **자원:** 초당 한 번의 CoreAudio 조회. 헬퍼의 CPU 사용량을 T0에서 잰다.

## 6. 성공 기준

- C1. 앱이 켜져 있을 때 Meet 입장 뒤 수 초 안에 카드가 위쪽 가운데에 뜨고, 다른 앱의 키보드 입력이 끊기지 않는다.
- C2. 카드의 `녹음 시작`으로, 담화 창을 앞으로 띄우지 않고 마이크+시스템 오디오 녹음이 시작된다.
- C3. Meet 음소거로 녹음이 멈추지 않는다.
- C4. Meet에서 나가면 약 10초 뒤 녹음이 멈추고, 전사·요약이 사용자 조작 없이 끝난다.
- C5. `닫기`, 시작 실패, 수동 종료 뒤 같은 회의에서 카드가 다시 뜨지 않는다.
- C6. 모달로 시작한 녹음 중에는 카드가 뜨지 않고 자동 종료되지 않는다. 담화 자신의 마이크로 카드가 뜨지 않는다.
- C7. Zoom·Teams는 T0 판정대로 동작한다(자동 종료 또는 시작만).
- C8. 메뉴에서 끄면 헬퍼가 끝나고 카드가 뜨지 않는다. 재시작 뒤에도 유지된다.
- C9. 서명된 패키지에서 권한 창 없이 감지가 동작하고 `check-bundle`이 헬퍼를 검사한다.
- C10. 앱 종료 시 헬퍼가 남지 않는다.
- C11. 마이크 연결이 끊긴 녹음은 `녹음 중`에 머물지 않고, 서버에서 마감된 뒤 `녹음이 중단됐어요`를 보여준다.
- C12. 감시 헬퍼를 녹음 중에 죽여도 녹음이 멈추지 않고, 재기동 뒤 자동 종료가 다시 동작한다.
- C13. 카드 시작 중에 모달 시작·창 닫기·앱 종료가 겹쳐도 마이크가 두 번 열리지 않고 빈 `recording` 회의가 남지 않는다.
- C14. 시스템 오디오가 녹음 중 끊기면 카드 표시가 `마이크만 녹음 중`으로 바뀐다.

## 7. 진행 순서

- **T0. 실측:** Zoom·Teams의 번들 ID와 음소거·종료 동작, 입장 전 미리보기의 입력 여부, 패널 창의 클릭·포커스, 제스처 없는 녹음 시작,
  `setContentProtection`, 헬퍼 CPU, **서명된 패키지에서의 헬퍼 기동·감지·권한 창 유무**. Teams가 없으면 사용자와 상의해 목록에서 뺀다.
- 그 뒤는 구현 계획에서 정한다.

## 8. 알려진 한계

- Chrome은 탭을 구분할 수 없어 Meet이 아닌 사이트의 마이크 사용에도 카드가 뜬다. `닫기`로 넘긴다.
- 카드로 시작한 녹음 중 Chrome의 다른 탭이 마이크를 잡고 있으면 회의가 끝나도 멈추지 않는다. `중지`로 끝낸다.
- 입장 전 미리보기에서 입력이 켜지면 카드가 입장 직전에 뜰 수 있다.
- 담화가 켜져 있고 창이 있어야 감지한다.
- 시스템 오디오 권한이 거부돼 있으면 상대 목소리가 0으로 녹음된다(기존 한계).
