# 공개 데모 배포 설계

**작성일:** 2026-09-01
**상태:** **설계 진행 중.** §2–§5는 확정, §6은 미결. 구현 착수 전에 §6을 닫고 이 문서를 완성한다.
**범위:** 이력서 링크로 걸 공개 데모 — 배포 형태, 방문자 격리, 시드 데이터

## 1. 목적과 성공 기준

Damwha는 지금까지 셀프호스팅 전제로만 돌았다. `deploy/README.md`의 설치 절차는 Docker
Desktop + uv + ffmpeg + Hugging Face 토큰 + 라이선스 3개 수락을 요구한다. 채용 심사자가
이력서를 보다가 이걸 따라 할 리 없다.

이 설계의 목적은 **링크 하나로 주요 기능을 확인할 수 있는 공개 데모**다. 대상 독자는
한국 채용 심사자이고, 링크에 쓰는 시간은 90초 안팎으로 잡는다.

성공 기준:

- 링크를 열면 로그인 없이 즉시 한국어 회의의 분석 결과 화면이 뜬다.
- 화자별 타임라인, 검색, 렌즈(액션·결정·약속), 요약, 메모를 실제로 조작할 수 있다.
- 한 방문자의 조작이 다른 방문자에게 보이지 않는다.
- 데모에 실린 오디오와 전사에 저작권·초상권 문제가 없다.
- 실제 오디오 처리가 클라우드에서 일어나지 않는다는 사실이 방문자에게 숨겨지지 않는다.
- 링크가 오래 살아 있다. 운영 부담과 비용이 예측 가능해야 한다.

## 2. 확정된 제약: ML 파이프라인은 클라우드에서 못 돈다

이 설계 전체가 이 제약에서 나온다. 근거는 코드에 있다.

- **GPU 경로가 MLX 전용이다.** `worker/damwha_worker/models/registry.py`의 `build_models`는
  `devices.stt`가 `gpu`면 `MlxWhisper`를 고른다. `models/device.py`의 `torch_device`는 MPS가
  없는 머신에서 `gpu` 요청을 **PERMANENT `gpu_unavailable`로 실패**시킨다. CPU 폴백은
  페이로드 재현성 때문에 의도적으로 없다.
- **렌즈·요약 LLM 런타임이 `mlx_lm.server`다.** `llm_server.py::managed_llm_server`가 그
  바이너리를 실행한다. Apple Silicon 전용이고 **리눅스 대체 백엔드가 아예 없다.**
- CPU 프리셋(`faster-whisper` int8 + pyannote CPU)만 이론상 리눅스에서 돌지만, 10분 회의에
  수십 분이 걸리고 렌즈·요약은 여전히 불가능하다.
- 익명 방문자에게 업로드를 열면 비용·저작권·악용이 통째로 열린다.

**결론:** 클라우드에는 Postgres + API + SPA만 올린다. 워커는 없다. 회의 결과는 개발자의
Mac에서 **진짜 파이프라인으로 미리 구워서** 시드로 넣는다.

이건 회피가 아니라 이 프로젝트의 설계 그 자체이므로, 데모에서 숨기지 말고 엔지니어링
결정으로 설명한다. `deploy/docker-compose.yml`이 이미 같은 분리(컨테이너 API + 호스트 워커)를
전제하고 있고, `CAPABILITIES_*` env가 존재하는 이유도 그것이다.

## 3. 확정된 결정

### 3.1 로그인은 만들지 않는다

`be/src` 전체에 인증 코드가 0줄이다. guard도, `user_id`/`tenant` 컬럼도 없다. 10개 컨트롤러
전 엔드포인트가 무인증이다. "로그인 여부로 라우터 분리"는 분리가 아니라 **인증 서브시스템을
새로 짓는 것**이고, 이력서 데모의 비용 대비 가치가 맞지 않는다. 방문자에게 회원가입은
이탈 지점이기도 하다.

### 3.2 방문자별로 격리한다

방문자는 로그인 없이도 렌즈 완료 체크, 화자 이름 변경, 메모 작성 같은 쓰기를 전부 할 수
있어야 한다. 그게 이 제품의 핵심 인터랙션이고, 읽기 전용 데모는 버튼마다 "데모에서는
비활성" 툴팁이 뜨는 인상 나쁜 화면이 된다.

공유 DB + 주기적 리셋도 검토했으나 **§3.3의 업로드 리플레이와 양립하지 않는다** — A가
업로드를 재생하는 순간 B의 회의 목록에 새 회의가 튀어나온다. 두 결정이 맞물려 있다.

격리 비용은 처음 우려한 것보다 낮다. 이 프로젝트는 **ORM이 없고 모든 DB 접근이
`DatabaseService`(`pg.Pool` 래퍼의 `query` / `withTransaction`) 한 곳을 통과**하므로,
repository SQL을 한 줄도 건드리지 않고 그 한 파일에서 격리를 끝낼 수 있다.

구현 방식은 **미결(§6.1)**.

### 3.3 업로드는 파일을 받지 않는다

업로드 모달은 열되 **파일 선택기를 제거**하고, 드롭존 자리에 "데모는 오디오를 받지 않습니다 —
샘플로 처리 흐름 재생" 안내와 버튼을 놓는다. 처리 설정 UI(프리셋·언어·디바이스)는 그대로
노출한다.

파일을 받아서 버리는 방식은 코덱스와 검토 과정에서 모두 반대했다. 근거: 심사자는 개발자다.
아무 파일이나 넣었는데 항상 같은 결과가 나오면 즉시 눈치채고, 그 순간 **나머지 결과물까지
가짜로 의심받는다.** 안내 문구가 있어도 마찬가지다. 받지 않으면 "저장 안 함"이 약속이 아니라
사실이 되고, 저장·용량·악성 파일 문제가 통째로 사라진다.

재생되는 것은 `queued → running(스테이지) → done` 전이이고, 결과는 미리 구운 회의가 붙는다.
실제 워커 없이 `job` 행의 `stage`/`status`만 타이머로 전진시키는 작은 서비스로 충분하다.

### 3.4 시드 오디오는 대본 기반 TTS 재연으로 만든다

조사 결과 **한국어 다화자 회의 오디오 중 공개 재배포가 허용되는 것은 존재하지 않는다**
(근거는 §4). 선택지는 직접 녹음과 합성뿐이고, **서로 다른 TTS 목소리 4개로 대본을 읽히고
약간씩 겹치게 믹싱하는 방식**으로 간다.

이 방식을 고른 이유:

- 사람 4명을 모으는 실물 녹음보다 리드타임이 짧고 재현 가능하다.
- NotebookLM Audio Overview보다 낫다 — 그쪽은 **화자가 최대 2명**이고(Deep Dive·Critique·
  Debate가 2인, The Brief가 1인), 말투가 회의가 아니라 팟캐스트라 **렌즈 추출이 거의 빈손으로
  돌아온다.** 이 제품에서 제일 인상적인 기능이 텅 빈 화면이 된다. 호스트 목소리가 널리 알려져
  즉시 합성으로 인지되는 문제도 있다. (약관 자체는 문제없다 — §4.3)
- 화자 수와 겹침을 직접 통제할 수 있어 화자 분리가 보여줄 게 남는다.

대본은 LLM으로 뽑되 **액션아이템 3개, 결정 1개, 이견 충돌 1개, 약속 1개**를 의도적으로
심는다. 렌즈와 요약이 뽑을 것이 대본에 이미 들어 있어야 결과 화면이 꽉 찬다.

**정직성:** 화면에 "대본 기반 재연 샘플"로 표기한다. 합성이라는 사실을 숨기지 않는다.

한계도 기록해 둔다. TTS는 맞장구·생활소음이 없어 화자 분리 입력으로는 실제 회의보다 쉽다.
`be/CLAUDE.md`에 기록된 duration-weighted centroid 작업(다른 화자 쌍 최악값 .674 → .619)이
보여줄 게 줄어든다. 겹침 믹싱으로 일부 상쇄한다.

### 3.5 회의 길이는 10–15분

`be/CLAUDE.md`에 발화 수가 프롬프트 비용을 지배한 이력이 있다. 라인 포맷 도입 전 mtg_10
(778발화)이 119,563자, mtg_3(997발화)이 236,484자였고 둘 다 LLM 타임아웃으로 죽었다.
라인 포맷 이후 각각 39,238자와 133,215자로 내려왔지만, 짧은 쪽이 안전하고 데모로도 잘 읽힌다.
10–15분이면 발화 150–250개 선이다.

### 4.3 NotebookLM 생성 오디오

약관상으로는 **사용 가능하다.** 구글은 2024-04부터 자사 AI 도구 출력물의 소유권을 주장하지
않고, Workspace 약관도 "Google does not assert any ownership rights in any new intellectual
property created in the Generated Output"이라고 쓴다. 상업적 이용도 허용되며 NotebookLM은
Audio Overview 다운로드·공유를 공식 지원한다.

제한 세 가지: (1) 출력물로 **경쟁 모델·서비스를 개발하는 것은 금지** — Damwha는 학습을 하지
않고 사전학습 모델로 추론만 하므로 해당 없으나, 이 오디오로 fine-tune하면 걸린다.
(2) Play Books 전자책을 소스로 쓴 노트북은 다운로드가 막힐 수 있다. (3) **소스 문서의
저작권은 그대로 남는다** — 대본을 직접 쓰면 깨끗하다.

**채택하지 않은 이유는 약관이 아니라 제품 적합성이다(§3.4).**

### 4.4 AMI를 쓸 경우의 의무 (보조 샘플로 채택 시)

- CC BY 4.0은 **저작자표시 + 라이선스 링크 + 변경 사실 명시**를 요구한다. GitHub README가
  아니라 **해당 샘플의 상세 화면과 푸터에 상시 노출**한다. 문안 예시:
  > English sample derived from the AMI Meeting Corpus, University of Edinburgh, CC BY 4.0.
  > Audio excerpt and transcript processed/modified by Damwha. [Source] [License]
- **CC BY는 초상권·퍼블리시티권·인격권을 부여하지 않는다.** AMI 참가자는 식별 가능한 실제
  인물이다. 화자명을 `Participant A~D`로 대체하고, 그들의 신원에 대한 주장을 하지 않으며,
  **AMI 음성으로 화자 등록/생체 식별 기능을 홍보하지 않는다.** 이 제품이 ECAPA 보이스프린트를
  DB에 영구 저장하므로 이 항목의 무게가 더 크다.

## 5. 90초 예산에서의 우선순위

심사자가 링크에 쓰는 시간은 90초 안팎이다. 그 안에 전달할 문장 하나:

> "한국어 회의에서 귀속 가능한 액션아이템·결정과 검색 가능한 타임라인을 뽑아냈다."

따라서 **랜딩은 한국어 회의의 결과 화면**이다. 업로드 흐름도, 설정도, 아키텍처 설명도,
화자 분리 차트도 아니다. 나머지는 전부 그 뒤를 받치는 증거로 배치한다.

## 6. 미결 사항 — 내일 이어갈 지점

### 6.1 방문자 격리 구현 방식 (최우선)

`DatabaseService` 한 곳에서 끝난다는 것까지는 정해졌으나 방식은 비교가 남았다. 후보:

- **세션별 Postgres 데이터베이스** (`CREATE DATABASE demo_x TEMPLATE damwha_seed`).
  TEMPLATE 복제가 빠르고 스키마·트리거·인덱스·시퀀스가 전부 그대로 온다. 격리가 확실하다.
  대신 세션별 커넥션 풀이 필요해 LRU 관리가 붙는다.
- **세션별 스키마** + 커넥션 획득 시 `search_path` 설정. 커넥션 수가 늘지 않는다. 대신
  풀 반환 시 `search_path` 누수 사고 위험이 있고, 마이그레이션 013/014의 deferred constraint
  trigger와 pgvector 인덱스까지 복제되는지 확인이 필요하다.

두 안 모두 **TTL GC**(N시간 미사용 시 DROP)가 필수다. GC가 실패하면 디스크가 찬다 —
링크가 오래 살아야 하므로 이건 운영 리스크로 다룬다.

오디오 파일(`STORAGE_ROOT`)은 격리 대상이 아니다. 데모 오디오는 공유 읽기 전용.

**코덱스 지적(미해소):** "세션 격리는 UI가 그렇게 말한다고 실재하는 것이 아니다. user/session
컬럼이 없는 상태에서 시드 행은 API의 id로 발견·수정·삭제될 수 있다." 격리 계층과 별개로
**변경 엔드포인트의 잠금 범위**를 명시해야 한다.

### 6.2 배포처와 비용 상한

미정. 필요한 것은 Postgres(pgvector + pg_bigm) + Node 컨테이너 하나. 검색의 의미 검색 경로는
쿼리 시점에 임베드 서비스를 호출하므로(`EMBED_SERVICE_URL`), 다음 중 하나를 골라야 한다:

- CPU 임베드 서비스를 같이 띄운다 (의미 검색 살아 있음)
- 띄우지 않는다 — 코드가 이미 BM25 키워드 검색으로 조용히 폴백한다 (`deploy/README.md` 참조)

### 6.3 시드 회의 구성 ~~최종안~~ — 한국어 부분은 닫혔다 (2026-09-01)

**한국어 4건으로 확정.** 대본은 `demo/scripts/`에 있고 `demo/README.md`가 캐스트·포맷·
회차 구성을 설명한다. 같은 팀 4명이 한 프로젝트를 4회에 걸쳐 진행하는 구성이라
**회의 간 화자 동일성**과 **액션아이템 후속 추적**이 둘 다 시연된다. 2회차에서 미룬 결정이
3회차에서 장애로 터지고 4회차에서 그 패턴을 근거로 출시를 연기하는 줄기를 심어, 검색과
렌즈가 회의를 가로질러 연결되는 것을 보여준다.

남은 것:

- **AMI를 보조 샘플로 넣을지.** 넣으면 다국어가 덤으로 증명되고 §4.4의 의무가 따라온다.
  `ES2002a+b`(같은 4명의 연속 회의)를 쓰면 회의 간 화자 동일성도 시연되지만, 한국어 4건이
  이미 그걸 하므로 **넣을 근거가 약해졌다.** 다국어 증명만을 위해 §4.4의 초상권 주의사항을
  떠안을 값어치가 있는지가 판단 지점이다. 코덱스는 "AMI 여러 파트는 padding"이라 했으나
  이는 AMI 구조를 오인한 것 — 무작위 2건이면 padding이 맞지만 같은 팀의 연속 파트는 기능
  그 자체다.
