# 더 좋은 STT 모델을 찾다가, 비교 기준부터 고치게 됐다

회의가 끝난 뒤 “누가 어떤 말을 했는지” 확인하고, 필요한 발언을 다시 듣기 위한 회의 기록 도구를 개발하고 있다. 녹음 파일을 넣으면 사용자의 컴퓨터에서 음성을 글로 옮기고, 발언마다 말한 사람과 녹음 시점을 표시한다. 음성을 텍스트로 바꾸는 기능을 STT라고 하며, 이 글에서는 그 결과를 ‘전사’라고 부른다.

이 도구에 새로운 음성 인식 모델인 Qwen3-ASR을 추가할지 검토했다. 기존에 사용하던 모델은 Whisper였다. 첫 비교에서는 새 모델의 결과가 좋아 보였지만, 기존 처리 과정의 반복 오류를 발견하고 수정한 뒤에는 모델 교체의 근거가 약해졌다. 최종적으로는 기존 처리를 보완하고 도입을 보류했다.

어떤 지표로 비교했고, 어떤 수정안을 기각했으며, 무엇을 확인한 뒤 판단을 바꿨는지 기록하려고 한다. 수치는 2026년 8월 로컬 실험 결과다. 비교에 사용한 참조 전사도 다른 음성 인식 서비스가 만든 텍스트이므로, 사람이 검수한 정답과는 차이가 있다.

## 글로 옮긴 단어가 언제 나온 말인지도 알아야 했다

프로젝트 이름은 담화다. 사용자는 전사 내용을 읽다가 발언을 선택해 해당 시점의 녹음을 다시 들을 수 있다. 또 여러 사람이 참여한 회의이므로 누가 말했는지도 표시해야 한다. 이 글에서 ‘화자’는 녹음에서 말한 사람을 뜻한다.

이를 위해 단어마다 녹음에서의 시작·종료 시각, 즉 타임스탬프가 필요했다. 예를 들어 어떤 단어가 12~13초에 있고, 별도로 분석한 결과 그 시간에 A가 말하고 있었다면 해당 단어를 A의 발언에 연결할 수 있다. 텍스트만 정확하고 시간이 없으면 이 연결이 어려워진다.

기존 처리 과정에서는 먼저 말소리가 있는 구간을 찾는 음성 활동 감지(VAD)를 사용했다. 무음까지 전사하지 않도록 입력 범위를 고르는 단계이며, 여기에 Silero라는 도구를 썼다. 찾은 구간은 Whisper의 `large-v3-turbo` 모델로 전사했다. 이후에는 이 모델을 ‘Whisper turbo’라고 부르겠다.

새 모델을 검토하면서 첫 제약을 만났다. 당시 Qwen을 실행하는 데 사용한 라이브러리인 mlx-audio는 해당 경로에서 단어별 시간을 반환하지 않았다. 출력에 구간 목록을 뜻하는 `segments` 필드가 있었지만, 30초 입력이 시작 0초·끝 30초인 구간 하나로 나왔다. 이것만으로는 그 안의 어떤 단어가 누구의 발언인지 구분할 수 없었다.

따라서 Qwen을 도입하려면 텍스트를 만든 뒤 각 단어를 오디오 시점에 다시 맞추는 ‘시간 정렬’ 단계가 추가로 필요했다. 먼저 텍스트 품질이 이 추가 작업을 감수할 만큼 좋아지는지 확인하기로 했다. 평가 코드에서도 임의의 시간을 채워 화자 연결을 시도하지 않고, 텍스트만 비교하는 별도 경로를 두었다.

## 먼저 무엇을 비교하는지 정했다

같은 음성 파일을 모델별로 전사하고, 결과와 처리 시간을 저장하는 평가 스크립트를 사용했다. ‘참조 전사’는 이 결과와 대조할 기준 텍스트다.

Whisper는 실제 서비스처럼 말소리가 있는 구간만 전사하는 조건을 기본으로 삼고, 전체 파일을 전사하는 조건도 따로 측정했다. Qwen은 당시 평가 코드에서 구간을 지정하는 같은 방식을 지원하지 않아 전체 파일을 전사했다. 이 입력 방식의 차이는 앞서 설명한 단어별 출력 시간의 부재와는 별개의 조건이다.

따라서 VAD를 사용하는 기존 방식과 Qwen의 비교는 **서비스의 전사 처리 방식을 교체했을 때 얻을 결과를 비교하는 실험**이다. 입력 구간까지 동일하게 통제한 모델 자체의 성능 비교는 아니므로, 표에 입력 조건을 함께 적었다.

주 지표는 문자 오류율(CER)로 잡았다. 전사 결과를 참조와 같게 만들기 위해 추가·삭제·교체해야 하는 문자 수를 참조의 문자 수로 나눈 값이다. 예를 들어 참조가 100자이고 문자 5개를 고쳐야 한다면 CER은 5%다. 값이 낮을수록 참조와 가깝다.

띄어쓰기나 문장 부호의 차이가 비교를 좌우하지 않도록, 두 텍스트에서 공백과 문장 부호 등을 같은 규칙으로 제거한 뒤 계산했다. 이처럼 비교 전에 표기를 일정하게 맞추는 처리를 정규화라고 한다.

처음 사용한 참조는 한국어 강연의 유튜브 자동 자막이었다. 사람이 검수한 정답은 아니었다. 실제로 참조가 고유명사를 잘못 적은 부분도 있었다. 따라서 CER은 이 참조와 얼마나 다른지를 보여주는 비교 신호로 사용했다. 다른 엔진의 출력이라고 해서 참조의 오류나 편향이 없어지는 것은 아니다.

## 강연에서는 새 모델이 좋아 보였다

한 사람이 말하는 약 17분짜리 한국어 강연을 비교했다. 아래 Qwen 1.7B는 이번에 검토한 모델의 크기를 구분하는 이름이다. 표에서는 모델 크기보다 CER과 처리 시간을 함께 봤다.

| 모델과 입력 조건 | CER | 기록된 전사 시간 |
| --- | ---: | ---: |
| Whisper turbo, VAD 구간 | 5.22% | 70.1초 |
| Whisper turbo, 전체 파일 | 7.68% | 49.0초 |
| Qwen3-ASR 1.7B, 전체 파일 | 4.59% | 148.1초 |

Qwen 1.7B 모델의 CER은 기존 VAD 경로보다 약 0.63%p 낮았다. 다만 전사 시간은 더 길었고, 시간 정렬 단계를 붙였을 때의 비용은 아직 포함되지 않았다. 이 표만으로 도입을 결정하기는 어려웠다.

표기 방식도 결과에 영향을 줬다. 함께 시험한 더 작은 Qwen 모델은 숫자를 한글로 풀어 쓰는 경향이 있었다. 참조의 숫자 표기를 바꾸자 기존 모델과의 순위가 뒤집혔다. 예를 들어 “1177년”과 “천백칠십칠 년”은 같은 내용을 표현해도 문자 비교에서는 다르게 계산된다. 그래서 한 가지 표기 조건의 순위만으로 후보를 고르지 않았다. 두 조건에서 모두 가장 낮은 CER을 보인 Qwen 1.7B를 후속 비교 대상으로 남겼다.

다음에는 담화의 실제 사용 상황인 여러 사람이 말하는 회의를 확인했다. 강연에서의 차이가 잡음과 짧은 발화가 섞인 회의에서도 유지되는지가 중요했다.

## 회의 녹음에서 비교보다 먼저 고칠 문제를 발견했다

약 29분짜리 회의 녹음은 처음에는 참조 전사가 없었다. CER을 계산할 수 없어, 출력에서 명확하게 드러나는 반복 오류부터 확인했다.

Whisper는 같은 문자열을 비정상적으로 길게 반복하는 결과를 냈다. 이런 출력을 여기서는 ‘반복 루프’라고 부르겠다. 출력 11,919자 중 3,783자, 약 31.7%가 이 반복에 해당했다. 0.3~2.3초짜리 구간에서 `CON` 같은 문자열을 수백 번 출력했다. 그 반복 단어 1,109개 중 1,045개는 시작과 끝 시간이 같았다. 실제로 사람이 말하는 데 시간이 걸린다는 점을 생각하면, 길이가 0초인 단어가 이렇게 몰리는 것은 시간 정보도 함께 망가졌다는 신호였다.

이 수치는 해당 회의의 한 실행에서 나온 관측값이다. 모든 회의에서 같은 비율로 오류가 발생한다는 뜻은 아니다. 하지만 사용자가 읽어야 할 발화에 이런 문자열이 쌓인다면 전사 결과를 사용하기 어렵다는 점은 분명했다.

처음에는 반복이 거의 없는 Qwen의 출력을 보고 회의에서도 더 낫다고 판단했다. 지금 돌아보면 그때 확인한 것은 기존 경로의 큰 결함이었다. 반복이 적다는 사실만으로 나머지 발화까지 더 정확하다고 결론 내릴 수는 없었다.

조사의 우선순위를 바꿨다. 모델 추가 여부를 결정하기 전에 기존 경로의 반복 오류를 재현하고, 수정한 뒤 다시 비교하기로 했다.

## 짧은 구간만 떼어내니 재현되지 않았다

모델이 음성을 바탕으로 출력할 문자열을 선택하는 과정을 디코딩이라고 한다. 처음에는 짧은 입력에서 디코딩을 재시도할 때 선택이 달라져 반복이 생기는지 의심했다. 문제가 발생했던 구간을 따로 떼어 72회 호출했지만 반복 루프는 한 번도 나오지 않았다. 문자열 선택의 무작위성에 관여하는 온도(temperature) 설정을 0으로 고정하거나 입력 구간을 늘려 봐도, 분리한 구간에서는 같은 증상을 재현하지 못했다.

반면 회의의 207개 구간을 연속 처리하면 문제가 다시 나타났다. 새 프로세스에서 세 번 실행했을 때도 매번 발생했지만, 위치와 반복 문자열은 달랐다.

| 실행 | 관측된 반복 예시 |
| --- | --- |
| 1 | `넣은` 111회, `넣은` 109회 |
| 2 | `반죽을` 55회, `max` 223회 |
| 3 | `입장` 111회 |

이 결과로 짧은 구간 하나만 실행하는 실험은 실제 실패 조건을 충분히 재현하지 못한다는 것을 알았다. 이후 검증은 회의 전체 구간을 연속 처리하는 조건으로 진행했다.

왜 연속 실행에서 발생 위치가 달라지는지까지 밝혀낸 것은 아니다. 당시 모델 계산에 쓰인 MLX라는 실행 라이브러리에서 같은 입력도 계산 결과가 조금씩 달라지는지 의심했지만, 이를 원인으로 확증하지 못했다. 다만 반복 출력이 생성됐을 때 기존 방어 로직을 통과하는 경로는 당시 라이브러리 코드에서 확인할 수 있었다.

## 반복을 감지해도 결과가 살아남는 경로가 있었다

사용한 `mlx-whisper 0.4.3`의 `transcribe.py`를 확인하니, 반복적인 출력을 감지하면 문자열을 선택하는 조건을 바꿔 다시 전사하는 로직이 있었다. 그런데 같은 구간을 말소리가 없는 입력으로 판단하면 그 재시도를 취소했다. 여기서 무음 확률은 모델이 해당 구간에 말소리가 없다고 추정한 값이다.

말소리를 찾아 자른 구간에서도 무음 판정이 나올 여지가 있었다. 짧은 입력도 모델에 넣을 때는 30초 길이로 빈 부분을 채웠다. 1초짜리 발화를 넣으면 나머지 대부분은 무음이 되므로, 앞 단계에서 말소리를 찾았다고 해서 모델의 무음 확률이 반드시 낮아지는 것은 아니었다.

그다음에는 무음 구간의 출력을 버리는 로직이 있었다. 다만 모델이 자신이 만든 문자열에 높은 확률을 부여하면 출력을 유지했다. 코드에서는 이 판단에 ‘평균 로그 확률’이라는 점수를 사용했다. 실제 정답과 대조한 정확도가 아니라 모델 내부에서 계산한 점수이므로, 높은 값이 올바른 전사를 보장하지는 않는다. 두 분기가 이어지면 다음 경로가 가능했다.

1. 반복적인 출력이라 재시도가 필요하다고 판단한다.
2. 무음 확률이 높다는 이유로 재시도를 취소한다.
3. 무음으로 보고 출력을 버리려 한다.
4. 평균 로그 확률이 높다는 이유로 출력을 유지한다.

출력에 기록된 단어별 신뢰도 점수인 `confidence`도 반복 단어에서 0.97~0.98까지 관측됐다. 이 값과 앞서 분기에 사용하는 평균 로그 확률은 서로 다른 지표다. 다만 반복 단어도 높은 점수를 받았으므로, 신뢰도가 낮은 단어만 삭제하면 이 오류를 놓치게 된다.

여기서 확인한 것은 **이미 생성된 반복 출력을 방어 로직이 걸러내지 못하는 조건**이다. 반복 생성 자체의 원인을 모두 설명한 것은 아니었다. 또한 이 설명은 확인한 mlx-whisper 구현에 한정한다. 다른 Whisper 구현은 재시도를 취소하는 조건이 다를 수 있다. 구체적인 코드와 비교 대상은 글 하단의 레퍼런스에 정리했다.

## 반복을 줄이는 설정이 다른 입력을 망가뜨렸다

먼저 무음 판정을 끄는 설정인 `no_speech_threshold=None`을 시험했다. 이 설정은 말소리가 없다는 판단을 근거로 동작하는 분기를 비활성화한다. 반복을 발견했을 때 재시도가 취소되지 않도록 하려는 시도였다.

반복은 줄었다. 설정을 바꾸기 전에는 실행마다 반복 구간이 2개, 2개, 1개였고, 설정을 바꾼 조건에서는 0개, 1개, 0개였다.

하지만 같은 설정은 무음 출력을 버리는 동작도 함께 껐다. 정상적으로 처리하던 강연을 다시 측정하니 CER이 5.07%에서 8.82%로 나빠졌다. 전사 단어 수도 1,994개에서 2,220개로 늘었다.

회의의 반복 오류만 보면 개선이었다. 강연에서는 불필요한 출력이 늘어났다. 이 설정을 공통 경로에 적용하면 기존에 잘 처리하던 입력이 나빠질 수 있어 채택하지 않았다.

이때부터 수정안의 기준은 반복 제거와 기존 입력의 품질 유지, 두 가지가 됐다. 문제가 난 파일만 다시 돌리는 것으로는 부족했다.

## 관측한 반복 패턴을 출력에서 걸러냈다

설정 변경의 부작용을 확인한 뒤, 모델이 반환한 결과를 서비스에 넘기기 전에 검사하는 후처리를 추가했다. 반복 횟수만으로 삭제하면 실제로 같은 말을 되풀이한 발화까지 지울 수 있어 시간 밀도도 함께 사용했다.

회의 전사 네 개, 약 14,000단어에서 연속 반복 분포를 확인했다. 정상으로 분류한 반복의 최대 길이는 5회였고, 6~10회 반복은 관측되지 않았다. 이상 반복은 11회 이상 구간에서 나타났으며, 짧은 시간에 수십~수백 단어가 몰려 있었다.

다음 두 조건을 모두 만족하는 연속 구간을 제거했다.

- 같은 텍스트가 6회 이상 이어진다.
- 해당 구간의 밀도가 초당 5단어를 초과한다. 길이가 0인 구간도 제거 대상으로 본다.

아래 코드는 같은 텍스트가 연속된 단어 목록 `run` 하나를 검사한다. 각 단어에는 시작·종료 시각이 밀리초 단위로 들어 있다. 먼저 6회 미만이면 보존하고, 나머지는 반복 횟수를 전체 구간의 초 단위 길이로 나눠 판단한다. 마지막 줄의 `True`가 해당 구간을 제거한다는 뜻이다.

```python
MIN_RUN = 6
MAX_WORDS_PER_SEC = 5.0

def _is_loop(run: list[Word]) -> bool:
    if len(run) < MIN_RUN:
        return False
    seconds = (run[-1].end_ms - run[0].start_ms) / 1000
    return seconds <= 0 or len(run) / seconds > MAX_WORDS_PER_SEC
```

예를 들어 “네”를 3초 동안 여섯 번 말하면 초당 2단어이므로 보존한다. 반면 같은 단어가 1초에 100번 몰려 있으면 두 조건을 모두 만족해 제거한다. 충분히 천천히 반복한 발화를 보존하는 테스트도 추가했다.

임계값은 이번 표본에서 정상 반복과 이상 반복을 구분하기 위해 선택한 값이다. 모든 언어와 발화 상황에서 성립하는 경계로 검증한 것은 아니다. 단어 시간이 잘못 추정되면 정상 반복을 삭제할 위험도 남는다.

또한 이 후처리는 망가진 전사를 복원하지 않는다. 반복 문자열이 저장되는 것은 막지만, 그 구간의 실제 발화는 별도로 복구해야 한다. 우선 사용하기 어려운 반복 출력을 줄이되, 제거한 내용을 복원했다고 간주하지 않기로 했다.

## 수정 후에는 원래 질문으로 돌아갔다

후처리 적용 후 같은 회의를 세 번 실행했을 때, 최종 출력의 반복 루프는 세 번 모두 0건이었다. 강연 CER은 5.27%였다. 앞서 관측한 5.07~5.22%보다 조금 높으므로 완전히 같은 결과라고 할 수는 없다. 다만 기각한 설정의 8.82%와 같은 큰 악화는 관측되지 않았다.

이후 같은 회의 녹음을 다른 음성 인식 서비스인 Clova Note가 전사한 결과를 참조로 확보해 비교했다. 이 참조 역시 사람이 검수한 정답이 아니므로, 아래 값은 해당 참조에 대한 CER이다.

| 전사 조건 | 실행별 CER | 평균 CER |
| --- | --- | ---: |
| Whisper turbo 수정 전 | 30.65%, 45.78%, 27.33%, 68.08% | 42.96% |
| Whisper turbo 수정 후 | 25.20%, 27.80%, 24.93% | 25.98% |
| Qwen 1.7B | 26.19%, 26.19%, 26.19% | 26.19% |

기록된 실행들의 평균 CER은 수정 전후 약 16.98%p 낮아졌다. 다만 동일한 회의 한 개를 반복 실행한 결과이며, 수정 전후 실행 수도 다르다. 이를 여러 회의에 대한 일반적인 개선율로 확대할 수는 없다.

모델 교체 판단에도 변화가 있었다. Qwen의 26.19%는 수정 후 turbo에서 관측된 24.93~27.80% 범위 안에 있었다. 이 데이터로 두 모델의 동등성을 입증할 수는 없지만, 처음 생각했던 Qwen의 뚜렷한 회의 전사 우위를 뒷받침하기도 어려웠다.

Qwen에는 별도의 시간 정렬 단계가 필요했다. 강연에서는 CER이 낮았지만, 이번 회의 표본에서는 그 추가 작업을 감수할 만큼의 텍스트 품질 우위를 확인하지 못했다. 그래서 당시에는 기존 Whisper 경로의 후처리를 유지하고 Qwen 도입을 보류했다.

이는 Qwen이 항상 느리거나 나쁘다는 결론이 아니다. 실제로 해당 회의의 초기 측정에서는 Qwen의 전사 시간이 더 짧았고, 후속 세 번의 CER도 같았다. 이런 관측은 남겨두되, 담화에 도입할 판단 근거와는 구분했다.

## 다음 비교에서는 기존 처리 방식의 실패부터 확인하려고 한다

처음에는 “새 모델이 더 좋은가”를 확인하려고 했다. 조사 중에는 “기존 경로가 어떤 입력에서 실패하는가”를 먼저 답해야 했다. 그 실패를 수정하자 처음의 비교 결과를 그대로 사용할 수 없게 됐다.

다음 모델을 검토할 때는 실제 사용 환경의 입력을 먼저 포함하고, 비교 기준으로 삼은 기존 처리 방식에 큰 결함이 있는지 확인하려고 한다. 결함을 발견하면 현재 상태의 비교 결과와 수정 후의 결과를 나눠 기록할 것이다. 텍스트 품질뿐 아니라 시간 정렬까지 포함한 전체 경로의 비용도 함께 측정해야 한다.

이번 수정에도 남은 일이 있다. 반복이 매번 다른 구간에서 발생하는 이유는 확증하지 못했고, 삭제한 구간의 실제 발화를 청취해 손실을 평가하지도 못했다. 사람의 검수 전사와 더 다양한 회의가 확보되면, 필터가 정상 발화까지 지우는 오탐 여부와 모델 간 품질 차이를 다시 확인할 필요가 있다.

기각한 설정과 그때 측정한 CER은 후처리 코드의 설명에도 남겼다. 나중에 같은 설정 변경을 검토하게 되면, 반복이 줄어든 결과뿐 아니라 강연 품질이 나빠졌던 근거도 함께 볼 수 있도록 했다.

## 레퍼런스

### 반복 출력이 걸러지지 않는 조건을 확인한 코드

이 글의 구현 분석은 로컬에 설치된 `mlx-whisper 0.4.3`을 기준으로 했다. 아래 mlx-whisper GitHub 링크는 글의 출처를 보강하면서 확인한 소스이며, 같은 두 조건 분기를 포함한다. 배포 패키지 전체와 동일한 커밋이라는 뜻은 아니다. 링크는 이후 코드가 바뀌어도 확인한 내용을 볼 수 있도록 커밋에 고정했다.

- [mlx-whisper의 전사 구현 — `transcribe.py`](https://github.com/ml-explore/mlx-examples/blob/796f5b53cab69a3d48a44233ce21aae889e94a08/whisper/mlx_whisper/transcribe.py): `decode_with_fallback`에서 반복 감지 후 `needs_fallback`을 무음 확률에 따라 다시 끄는 부분과, 전사 루프에서 평균 로그 확률에 따라 `should_skip`을 끄는 부분을 확인할 수 있다. 짧은 입력을 고정 길이에 맞추는 `pad_or_trim` 호출도 같은 파일에 있다.
- [faster-whisper v1.2.1의 전사 구현](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py): **차이를 확인하기 위한 비교 자료**다. `generate_with_fallback`은 재시도를 취소할 때 높은 무음 확률뿐 아니라 낮은 평균 로그 확률도 요구한다. 따라서 본문의 분기 설명을 모든 Whisper 구현에 그대로 적용할 수는 없다.

### 평가 지표와 사용한 도구의 공식 자료

- [JiWER 문서](https://jitsi.github.io/jiwer/): 문자 오류율(CER)과 단어 오류율을 계산하는 라이브러리다. 본문에서 사용한 전사 비교 지표와 텍스트 전처리 기능을 확인할 수 있다.
- [Silero VAD 공식 저장소](https://github.com/snakers4/silero-vad): 음성에서 말소리가 있는 구간을 찾는 도구다. 본문에서 전사할 입력 구간을 선택하는 단계에 해당한다.
- [Qwen3-ASR 공식 저장소](https://github.com/QwenLM/Qwen3-ASR): 음성 인식 모델과, 전사 텍스트를 음성 시점에 맞추는 ForcedAligner 사용법을 제공한다. 모델 도입 시 시간 정렬이 어떤 추가 단계인지 참고할 수 있다. 본문에 적은 단어별 시간의 부재는 **당시 시험한 mlx-audio 실행 경로의 제약**이며, Qwen의 모든 실행 방식에서 시간 정보를 얻을 수 없다는 뜻은 아니다.

이 공식 자료들은 도구와 구현을 이해하기 위한 참고 자료다. 본문의 CER·처리 시간·반복 횟수는 아래 프로젝트 실험 기록에서 가져왔다.
