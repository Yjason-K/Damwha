# STT 반복 루프 조사 보고서

**작성일** 2026-08-13 · **범위** `worker/damwha_worker/models/whisper_*.py`, `worker/damwha_worker/pipeline/stt_repetition.py`

## 요약

Qwen3-ASR 도입 검토를 위해 STT 성능을 재는 과정에서, **현재 프로덕션 STT가 실제 회의 녹음에서 전사 문자의 31.7%를 환각으로 채우고 있다**는 사실을 발견했다. 원인은 upstream Whisper의 안전망 두 개가 같은 성질 하나에 함께 무력화되는 구조였다. 어댑터 출력에서 축퇴 구간을 걷어내는 후처리를 추가해 회의 3회 연속 0건으로 막았고, 깨끗한 오디오에서는 필터가 발동하지 않는 것(오탐 없음)을 확인했다.

Qwen3-ASR 1.7B는 두 오디오 모두에서 `large-v3-turbo`보다 나았으나, **word timestamp를 내지 못해 도입은 보류**다.

> **정정 (같은 날 후속 측정).** 위 문장의 "두 오디오 모두"는 틀렸다. 회의 오디오의 참조 전사를 확보해 다시 재자 **실사용처에서는 동률**이었다 — Qwen의 우위는 turbo의 반복 루프가 만든 착시였고, 그 결함을 고치자 사라졌다. 원문은 조사 시점의 판단으로 남기고 근거는 [9장](#9-후속-측정--참조-확보-후-회의-오디오-2026-08-13)에 적는다.

## 1. 배경

`mlx-community/Qwen3-ASR-{1.7B,0.6B}-bf16`을 STT 선택지로 추가할지 판단하기 위해, 기존 `scripts/eval_stt.py`에 두 모델을 추가하고 CER/WER을 측정했다.

측정 도중 Qwen3-ASR이 **word timestamp를 내지 못한다**는 사실이 확인됐다. mlx-audio의 `STTOutput.segments`는 발화 구간이 아니라 청크 경계(`chunk_duration` 기본 1200초)로, 30초 슬라이스가 세그먼트 1개(`start=0.0, end=30.0`)로 나온다. `align.build_utterances`는 단어 중점으로 화자를 배정하므로(`_segment_for`), 이대로는 `Transcriber` 프로토콜을 만족시킬 수 없다.

따라서 eval은 **텍스트 품질만** 재도록 설계했다. `eval_stt.py`의 qwen 경로는 `Transcriber`를 흉내 내지 않고 텍스트만 돌려주는 `qwen_transcribe()`로 두었다.

## 2. 1차 측정 — 한국어 강연 17분, 단일 화자

기존 실측(2026-08-09)과 같은 wav를 쓰고, 참조 자막은 `yt-dlp`로 재수집했다.

| 조건 | 모델 | CER | WER | 시간 |
|---|---|---|---|---|
| 전체 파일 | qwen17 | **4.59%** | 18.71% | 148.1s |
| 가드, VAD clip | turbo | 5.22% | 21.26% | 70.1s |
| 전체 파일 | qwen06 | 5.72% | 19.96% | 86.9s |
| 가드, 전체 파일 | turbo | 7.68% | 23.71% | 49.0s |

turbo 두 줄은 2026-08-09의 5.07% / 7.68%를 재측정한 것으로, 전체 파일은 소수점까지 일치했다.

**표기 규약이 CER을 0.5%p씩 흔든다.** 0.6B만 숫자를 한글로 풀어쓴다("1177년" → "천백칠십칠 년"). 참조의 숫자를 한글로 바꿔 다시 재면 순위가 뒤집힌다(turbo 5.74% / qwen17 5.09% / qwen06 5.17%). **qwen17만 두 표기 조건 모두에서 1등**이므로, 0.6B는 turbo와 동급으로 보고 탈락시켰다.

이 단계의 결론은 "1.7B가 0.6%p 낫다"였고, 실사용처(다화자·잡음)에서도 유지될지는 미지수였다.

## 3. 2차 측정 — 실제 회의 녹음 29분, 다화자

참조 전사가 없으므로 CER은 낼 수 없다. 대신 **텍스트만으로 판정 가능한 파국적 실패**를 셌다.

| | turbo | qwen17 |
|---|---|---|
| 전체 문자 | 11,919 | 8,325 |
| 반복 루프 문자 | 3,783 (**31.7%**) | 8 (0.1%) |
| 루프 제거 후 | 8,136 | 8,317 |
| 전사 시간 | 287.3s | 218.7s |

turbo가 5개 구간에서 리터럴 `CON`을 각각 약 223단어씩 쏟아냈다(전체 4,429단어 중 1,109개 = 25%). 각 구간의 실제 오디오는 0.3–2.3초에 불과했고, **1,109개 중 1,045개가 길이 0초**였다.

세 가지가 확인됐다.

1. **confidence로 못 거른다.** 루프 단어의 max confidence가 0.97–0.98이다. 2026-08-09에 기록한 "반복 루프는 conf 0.95였다"보다 오히려 높다.
2. **루프를 걷어내면 두 모델의 실질 분량이 같다**(8,136 vs 8,317자). 같은 회의를 비슷한 밀도로 받아썼고 turbo만 쓰레기를 덧붙였다는 뜻이다.
3. **강연에서 안 보이던 문제다.** 같은 모델이 강연에서는 5.22%로 멀쩡했다. 우려했던 "회의에서 격차가 좁아질 가능성"과 반대로, 격차가 벌어졌다.

이 시점에서 조사의 우선순위가 바뀌었다. Qwen 도입 여부와 무관하게, **현재 프로덕션이 이 회의를 처리하면 utterance의 상당수가 `CON CON CON...`이 된다.**

## 4. 근본 원인

### 재현과 기각된 첫 가설

첫 가설은 "짧은 clip + temperature fallback의 비결정성"이었고, **기각됐다**. 문제의 span들을 격리해 72회 호출했으나 루프는 0건이었고, 각 조건 안에서 완벽히 결정적이었다(전부 같은 단어 수). `temperature=0.0` 고정도, span을 8초로 늘리는 것도 결과를 바꾸지 못했다.

실제로 터지는 층위는 **207개 clip을 연속 처리하는 배치**였다. 새 프로세스에서 3회 재현한 결과:

| run | 루프 span | 길이 | 반복 토큰 × 횟수 |
|---|---|---|---|
| p1 | #176, #192 | 1.58s, 0.75s | `넣은`×111, `넣은`×109 |
| p2 | #43, #204 | 0.84s, 2.83s | `반죽을`×55, `max`×223 |
| p3 | #138 | 1.26s | `입장`×111 |

반복 횟수 **223 / 111 / 55**는 토큰 수의 역수다 — `max`(1토큰)→223, `넣은`(2토큰)→111, `반죽을`(4토큰)→55. 전부 `sample_len = n_text_ctx // 2 = 224`(`mlx_whisper/decoding.py:419`) 상한까지 돌다 멈춘 것이다.

### 두 안전망이 함께 뚫린다

짧은 VAD span은 30초 창으로 패딩되어 대부분 무음이 되므로 `no_speech_prob`가 높다. `mlx_whisper/transcribe.py`에서:

```python
# 237-241
if compression_ratio_threshold is not None and decode_result.compression_ratio > compression_ratio_threshold:
    needs_fallback = True   # too repetitive   ← 반복을 잡아냄
...
if no_speech_threshold is not None and decode_result.no_speech_prob > no_speech_threshold:
    needs_fallback = False  # silence          ← 그 판정을 무효화
```

```python
# 301-309
should_skip = result.no_speech_prob > no_speech_threshold
if logprob_threshold is not None and result.avg_logprob > logprob_threshold:
    should_skip = False     # 무음이어도 logprob 높으면 안 버림
```

반복은 `compression_ratio`에 걸리지만 "무음이니까"로 판정이 뒤집혀 **temperature fallback이 아예 돌지 않는다.** 그다음 무음이라 버려질 차례인데, 반복 루프는 확신에 차 있어(`avg_logprob` 높음) 다시 살아난다. 관측된 conf 0.96–0.98이 그 값이다.

즉 **"모델이 쓰레기를 확신한다"는 성질 하나가 두 방어를 동시에 뚫는다.**

`faster_whisper/transcribe.py:1513, 1223`에 같은 로직이 있다. 이는 OpenAI Whisper 원본 로직이라 두 포트가 함께 물려받았고, 따라서 **`devices.stt=cpu`는 회피로가 아니다.**

## 5. 기각한 수정 — `no_speech_threshold=None`

`needs_fallback = False # silence` 분기를 죽이면 반복 판정이 살아난다. 실제로 효과가 있었다.

| 조건 | 루프 span (run당) |
|---|---|
| 대조군 | 4, 2 |
| 어댑터 기준선 | 2, 2, 1 |
| `no_speech_threshold=None` | 0, 1, 0 |

**그러나 같은 인자가 무음 스킵도 함께 끈다.** 참조가 있는 강연 오디오로 회귀를 재자 **CER 5.07% → 8.82%**, 단어 1994 → 2220으로 악화됐다. 무음 구간에 환각이 붙은 것이다.

파라미터로 두 효과를 분리할 수 없다. 값을 1.1로 올려도 `no_speech_prob ≤ 1.0`이라 None과 같고, 낮추면 fallback이 아예 죽는다. **루프 85% 감소를 CER 3.75%p로 사는 거래라 기각했다.**

## 6. 채택한 수정 — 출력 후처리

근본 원인은 우리가 소유하지 않은 upstream 코드에 있고, 설정으로 우회하는 길은 측정으로 손해가 확인됐다. 남은 선택은 어댑터 층에서 결과를 거르는 것이다.

`pipeline/stt_repetition.py::drop_repetition_loops` — 순수 함수. 두 조건을 **모두** 요구한다.

- 동일 텍스트 **6회 이상 연속**
- 그 구간의 밀도가 **초당 5단어 초과**

임계값은 추측이 아니라 실측에서 정했다. 회의 전사 4개(약 14,000단어)의 연속 반복 길이 분포:

| 길이 | 건수 | 예 |
|---|---|---|
| 2회 | 35 | |
| 3회 | 1 | `그리고` |
| 4회 | 4 | `태양은`, `반죽을` |
| 5회 | 5 | `또` |
| **6–10회** | **0** | |
| 11회 이상 | 11 | `하진진진`, `반죽을`×55, `넣은`×111, `CON`×223 |

정상 반복의 최대는 5회였고 6–10회는 한 건도 없었다. 밀도 조건은 루프가 55–223단어를 1–3초에 몰아넣는(65–147단어/초) 반면 사람은 낼 수 없는 속도라는 데서 왔다. 이 조건 덕분에 "네"를 3초에 걸쳐 여섯 번 말한 경우는 남는다.

교차 검증으로 길이 0초 비율도 확인했다 — **루프 안 93.8%, 루프 밖 0.7%.** 두 신호가 독립적으로 일치한다.

두 어댑터에 모두 걸었다. faster-whisper가 같은 upstream 로직을 갖기 때문이다.

## 8. 남은 것

**루프는 비결정적이다.** 같은 파일·같은 파라미터로도 매 run 다른 span에서 터진다(격리 호출 72회 0건, 207-clip 배치 run당 1–5건). MLX 수치 비결정성을 의심하지만 확증하지 않았다. 이 필터는 결과를 걷어낼 뿐 발생 자체를 막지 못하므로, 발생률이 오르면 다시 봐야 한다.

**루프가 났던 span의 실제 발화는 복구되지 않는다.** 해당 span들의 원 출력은 `CON`×223 + "감사합니다" 형태라 잃은 내용은 거의 없어 보이지만, 청취로 확인하지는 않았다.

**Qwen3-ASR 1.7B 도입은 보류다.** 두 오디오 모두에서 turbo보다 나았고 회의에서는 격차가 컸지만, word timestamp 관문이 그대로다. `Qwen3-ForcedAligner-0.6B`를 2단 체인으로 얹어야 하고, 5분 제한 때문에 VAD span 단위 정렬이 강제된다. 별도 설계가 필요하다. *(→ 9장에서 근거가 더 약해졌다.)*

**회의 오디오의 미판정 불일치.** 루프를 뺀 불일치 블록 194개(4자 이상)는 참조가 없어 판정하지 못했다. 두 모델의 실제 정확도 우열은 미결이다. *(→ 9장에서 해소됐다.)*

## 9. 후속 측정 — 참조 확보 후 회의 오디오 (2026-08-13)

8장이 남겨둔 "미판정 불일치 194건"을 풀기 위해, 같은 회의 녹음의 **Clova Note 전사**를 참조로 확보했다. 화자·시각 줄과 `clovanote.naver.com` 푸터를 제거해 8,583자를 얻었다.

**참조 자체가 ASR 출력이다.** 유튜브 자동 자막과 같은 한계이므로 절대 정확도가 아니라 상대 비교로만 읽는다. 다만 turbo/qwen 어느 쪽과도 무관한 제3의 엔진이라 한쪽에 편향될 이유는 없다.

| 전사 | run별 CER | 평균 |
|---|---|---|
| turbo 수정 전 | 30.65 / 45.78 / 27.33 / 68.08% | **42.96%** |
| turbo 수정 후 | 25.20 / 27.80 / 24.93% | **25.98%** |
| qwen17 | 26.19 / 26.19 / 26.19% | **26.19%** |

### 결과 1 — 수정 효과가 CER로도 확인됐다

회의 CER이 **42.96% → 25.98%**(상대 40% 감소). 7장의 검증은 "루프 span 개수"와 "강연 CER 무회귀"로만 확인했는데, 이제 **수정이 실제 전사 품질을 끌어올린다**는 직접 증거가 생겼다.

### 결과 2 — Qwen의 회의 우위는 착시였다

qwen17의 26.19%는 수정 후 turbo의 범위(24.93–27.80%) 안이고, 평균으로는 0.21%p 뒤진다.

| 오디오 | turbo (수정 후) | qwen17 |
|---|---|---|
| 강연 17분 · 단일 화자 | 5.22% | **4.59%** |
| 회의 29분 · 다화자 | **25.98%** | 26.19% |

3장에서 "회의에서 격차가 벌어졌다"고 본 것은 **turbo의 반복 루프를 보고 내린 판단**이었다. 그 결함을 고치자 격차가 사라진다. Qwen이 이기는 것은 깨끗한 단일 화자 오디오뿐이고, 그 대가로 2배 느린 디코딩과 ForcedAligner 2단 체인이 붙는다.

**결론: 실사용처에서 동률이므로 Qwen3-ASR 1.7B 도입 근거는 약하다.**

### 남는 관측 — 재현성

qwen17은 3회 모두 12,293자, CER 26.19%로 **완전히 동일**했다. turbo는 같은 조건에서 2.9%p 퍼진다(24.93–27.80%). 이 저장소는 payload 재현성을 설계 가치로 두고 있으므로(`devices.stt=gpu` 요청 시 CPU fallback을 금지하는 근거) 무의미한 차이는 아니다. 다만 3회로 결정성을 단정할 수는 없다.

### 방법론 메모

이 장의 교훈은 **결함이 있는 기준선과의 비교는 비교가 아니라는 것**이다. 3장의 회의 측정은 turbo가 전사의 31.7%를 환각으로 채운 상태에서 이뤄졌고, 그 상태로 "Qwen이 낫다"는 결론을 냈다. 참조가 없어 CER을 못 낸 것이 직접 원인이지만, 더 근본적으로는 **한쪽이 고장 난 것을 알면서도 그 비교를 결론으로 옮긴 것**이 문제였다. 고칠 수 있는 결함을 발견했다면, 비교는 고친 뒤에 다시 해야 한다.
