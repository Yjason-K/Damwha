# 화자 귀속 개선 조사 보고서 — 겹침 구간·발언 조각·align 진행률

**작성일** 2026-09-29 · **범위** `worker/damwha_worker/pipeline/align.py`, `pipeline/speaker_arbiter.py`, `pipeline/progress.py`, `pipeline/process_meeting.py`, `worker/scripts/eval_speaker_attribution.py`

## 요약

말이 빈틈없이 이어지는 대화에서 **B가 A의 말에 바로 이어 말하면 B의 첫마디가 A의 발언으로 기록되는** 증상을 클로바노트 전사와 대조해 측정하고 세 단계로 고쳤다.

1. **겹침 규칙 수정.** pyannote가 두 화자 구간을 겹치게 내놓으면 align은 겹친 자리의 단어를 *더 긴 구간*의 화자에게 줬다. 길게 말하던 A의 구간이 B의 시작을 덮는 것이 겹침의 전형이라, B의 첫마디가 체계적으로 A에게 갔다. *더 늦게 시작한 구간*으로 바꿔 첫마디 누수를 22.7% → 18.2%로 줄였다.
2. **조각 흡수.** 1의 부작용으로 여러 명이 겹치는 구간에서 화자가 단어 하나씩 번갈아 바뀌어 한두 단어짜리 발언이 쏟아졌다(실사용 녹음에서 두 단어 이하 발언 52 → 101개). 짧은 조각을 목소리가 더 가까운 앞·뒤 화자에게 붙이도록 해, 조각을 수정 전보다도 줄이고(15.1% → 13.5%) 정확도도 올렸다.
3. **align 진행률.** 처리 화면이 90%에 수 분간 멈췄다가 갑자기 끝나는 문제를 조사했다. align 단계의 임베딩 판정자가 같은 구간을 평균 28번씩 다시 임베딩하고 있었다(11,157회 중 서로 다른 구간 403개). 캐시로 align을 443초 → 16초로 줄이고, 그 사이 진행률을 90 → 95%로 흘리도록 했다.

4개 녹음(3시간 27분) 평균, 수정 전 → 최종:

|---|---|---|

**클로바노트도 ASR + 화자 분리 결과다.** 정답지가 아니라 비교 기준으로 쓰며, 아래 수치는 변형 간 상대 비교로 읽는다.

### 1.2 채점 도구 — `scripts/eval_speaker_attribution.py`

`eval_diarization.py`는 사람이 라벨링한 RTTM이 있어야 하고 `eval_stt.py`는 텍스트만 본다. 사용자가 실제로 보는 "이 문장이 맞는 사람 밑에 있는가"를 재는 도구가 없어서 새로 만들었다.

1. **cache** — 워커와 같은 순서(VAD → pyannote → ECAPA → Whisper turbo, VAD 구간만 전사)로 모델을 한 번 돌리고 align 입력을 JSON으로 저장한다. pyannote의 regular·exclusive 출력을 둘 다 저장한다.
2. **score** — 캐시에서 align 변형별로 발언을 다시 만들고, 우리 텍스트와 클로바 텍스트를 **글자 단위로 정렬**한다(한글을 자모로 풀어 edlib NW 정렬, 공백·문장부호 제외). 일치한 글자마다 화자를 비교하며, 라벨 대응은 DER처럼 헝가리안 1:1 매핑이다.

| 지표 | 뜻 |
|---|---|
| attr | 일치한 글자 중 화자가 맞은 비율 (화자 귀속 정확도) |
| **head→prev** | 클로바에서 A→B로 바뀔 때 B의 첫 12글자 중 A에게 붙은 비율 — **이번 증상 그 자체** |
| tail→next | A의 마지막 12글자 중 B에게 붙은 비율 |
| turn | 클로바 턴 중 다수결 화자가 맞은 비율 |
| leaks | B의 첫마디 절반 이상이 A에게 간 턴 수 |
| short | 우리 발언 중 두 단어 이하 비율 — 화면이 얼마나 잘게 쪼개져 보이는가 |

모델은 한 번만 돌리고 align만 바꿔 재므로, 모든 비교는 **같은 pyannote·Whisper 출력** 위에서 이뤄졌다.

## 2. 1단계 — 겹침 구간 규칙

### 2.1 원인

「거짓말은 나쁜 것일까」 00:46, 클로바 기준 참석자 2의 "물 없이 먹는 거 쉽지 않아":

```
SPEAKER_03  46.27s ─────────────────────────── 49.96s
SPEAKER_01          46.71s ──────── 47.67s
Whisper       "물 없이 먹는 거 쉽지 않아요"  46.14–47.64s
```

**pyannote는 두 번째 화자를 정확히 잡았다.** 그러나 단어 중점이 두 구간 모두에 들어가자 `_segment_for`가 더 긴 SPEAKER_03을 골랐고, 참석자 2의 말이 앞 화자 발언에 합쳐졌다.

"더 긴 구간이 이긴다"는 `f1f6586`(백채널이 본 화자의 단어를 빼앗는 문제 수정)에서 들어왔다. A가 길게 말하는 도중 짧은 호응 B가 끼는 경우를 막으려던 것이다. 그러나 흔한 겹침은 반대 모양이다 — pyannote는 **앞 화자 구간의 끝을 다음 화자의 시작 위로 늘려** 내놓는 경우가 많고, 이때 겹친 자리는 대개 새로 말을 시작한 B의 것이다. 백채널 쪽 위험은 같은 커밋의 `_smooth_backchannels`(이후 임베딩 판정자)가 이미 따로 다룬다.

### 2.2 변형 비교 (「거짓말은 나쁜 것일까」)

| 변형 | head→prev | turn | 비고 |
|---|---|---|---|
| longest (기존) | 22.7% | 70.6% | |
| shortest | 19.6% | 75.8% | attr 0.914로 하락 |
| exclusive (pyannote 겹침 없는 출력) | 20.9% | 73.1% | |
| **latest (채택)** | **15.9%** | **77.3%** | |
| latest + 판정자 끔 | 20.9% | 72.3% | 이득 대부분 소실 |

판정자를 끄면 이득이 사라진다. `latest`가 백채널 쪽에서 새로 만드는 오류를 판정자가 되돌리고 있어, 두 장치가 함께 있어야 성립한다.

### 2.3 이 규칙으로 못 고치는 원인

같은 녹음 00:37~00:46에서 pyannote는 **세 사람의 빠른 주고받기를 SPEAKER_03 한 명으로** 내놓았다(37.6~45.9s 연속 구간). 화자 분리가 전환 자체를 놓친 경우라 align이 할 수 있는 일이 없다. 최종 뒤에도 남은 누수 턴의 주력이 이 유형으로 보인다.

같은 오디오(「제발 저에게 말할 시간을 주세요」)를 앱에서 두 번 처리한 회의를 DB에서 꺼내 같은 방식으로 채점했다.

|---|---|---|
| 처리 | 2026-08-25, 수정 전 규칙 | 2026-09-29, 1단계 규칙(`a7646ea`) |

- 두 회의의 점수는 오프라인 측정의 `longest`/`latest`와 **소수점 수준까지 같다**(mtg_41 head→prev 18.97% vs 오프라인 18.95%, leaks 60 = 60). 화자 수 지정과 8월 이후의 다른 변경은 귀속 점수에 거의 영향이 없었고, 평가 도구가 실제 앱 결과를 예측한다는 것이 확인됐다.

- **부작용이 드러났다.** 두 단어 이하 발언이 52 → 101개로 늘었다. 02:13 구간:

```
mtg_41  04 경고 드리겠습니다 자꾸 / 00 말씀하시는데 / 01 경고예요 / 00 단호하게 / 01 가겠습니다 쓰고… / 04 같아요…
```

여러 명이 겹치는 구간에서 pyannote 구간이 여러 겹으로 나오면, 단어마다 "가장 늦게 시작한 구간"을 고르는 규칙이 화자를 단어 단위로 번갈아 바꾼다. 수정 전에는 같은 구간이 한 화자로 뭉쳐 있었다(틀렸지만 읽기는 편했다).

## 4. 2단계 — 조각 처리 방식 비교

### 4.1 클로바노트는 어떻게 하나

공개 자료(LINE DEVDAY 2021 발표)에 따르면 클로바노트의 화자 분리는 발화 구간 검출 → 화자 특징 추출 → 대조 학습 DNN 임베딩 → 클러스터링이고, 녹음 후 참석자 수를 입력받는다. 우리 파이프라인(Silero VAD → pyannote → ECAPA)과 큰 틀이 같다. **단어를 화자에 붙이는 방식과 조각 처리는 공개되지 않았다.**

출력만 보면 차이가 크다. 클로바의 두 단어 이하 턴은 6~10%인데 mtg_41은 27%였다. 클로바는 문장 정도의 단위로 끊고 그 단위에 화자 하나를 주는 것으로 보인다(관찰에 따른 추정).

### 4.2 후보

같은 캐시에서 두 방향을 시험했다. 모두 1단계 규칙(`latest`) 뒤에 붙는 후처리다.

| 후보 | 방법 |
|---|---|
| **조각 흡수** | 두 단어 이하이거나 1초 미만인 run을 앞·뒤 화자 중 목소리(ECAPA centroid 코사인)가 더 가까운 쪽에 붙인다. 자기 화자가 최선의 이웃보다 0.05 이상 가까우면 그대로 둔다 |
| 문장 단위 (다수결) | Whisper 문장 경계(`. ? !` 또는 1초 이상 쉼)로 단위를 끊고, 단위 안 화자가 여럿이면 시간 다수결로 하나를 준다. 양쪽 모두 3단어·1.5초 이상인 진짜 전환은 유지 |
| 문장 단위 (목소리) | 위와 같되 단위 전체를 임베딩해 가장 가까운 화자를 준다 |

### 4.3 결과 (4개 녹음 평균)

| | latest | **조각 흡수** | 문장 (다수결) | 문장 (목소리) |
|---|---|---|---|---|
| attr | 89.85% | **90.36%** | 84.74% | 85.52% |
| head→prev | 18.20% | **18.16%** | 23.58% | 22.79% |
| turn | 74.21% | **74.89%** | 63.20% | 64.26% |
| 두 단어 이하 발언 | 25.1% | 13.5% | 6.8% | **6.4%** |
| 발언 수 (클로바 1,537) | 1,645 | **1,409** | 986 | 998 |

문장 단위는 조각은 가장 적지만 정확도가 5%p 떨어지고, 첫마디 누수가 수정 전(22.7%)보다 나빠진다. 02:13 구간을 보면 이유가 분명하다.

```
조각 흡수  04 경고 드리겠습니다 자꾸 말씀하시는데 경고예요 / 01 단호하게 가겠습니다 쓰고 시작해야 될 것 / 04 같아요…
문장 단위  04 [119.0~143.9s, 25초 한 덩어리] 아무튼 시간은 지금 흘러가고 있으니까 … 레드카드
```

**Whisper는 빠른 주고받기 구간에서 문장부호를 거의 찍지 않는다.** "문장"이 수십 초짜리가 되고 그 안의 여러 사람이 한 사람으로 합쳐진다. 문장부호가 제대로 찍힌 곳(11:48 "알고 계셨어요? … 근데 왜 그러셨어요?")에서는 문장 단위가 가장 자연스럽게 끊었지만, 전체로는 쓸 수 없다. 클로바는 Whisper 문장부호보다 훨씬 정확한 경계를 따로 쓰고 있을 것이다.

**조각 흡수를 채택했다.** 정확도와 가독성을 함께 올린 유일한 후보였다.

### 4.4 적용

- `align._absorb_fragments` — 백채널 스무딩 뒤에 실행. 조각마다 `resolve_fragment(start, end, own, candidates)`를 묻고, 자기 라벨이면 유지·이웃 라벨이면 이동·`None`(임베딩 불가)이면 시간상 더 가까운 이웃에게 붙인다. 이동하면 처음부터 다시 훑으며, 이동마다 run이 하나씩 줄어 반드시 끝난다.
- `speaker_arbiter.make_fragment_resolver` — 짧은 스팬은 300ms까지 늘려 임베딩(ECAPA는 100ms 미만을 거부)하고, 같은 스팬은 한 번만 임베딩한다.
- `process_meeting`이 resolver를 만들어 넘긴다. `resolve_fragment`를 안 넘기는 호출(기존 테스트, 다른 호출부)은 동작이 그대로다.

- **match 수치 주의.** 1단계부터 match가 약 1%p 낮은데 텍스트를 잃은 것이 아니다. 발언은 시작 시각 순으로 정렬되므로 단어의 화자가 바뀌면 겹친 발언들의 순서가 달라지고, 순서에 민감한 글자 정렬이 그만큼 덜 맞는다. 단어 수는 같다.

## 5. 3단계 — align 진행률이 90%에서 멈추는 문제

### 5.1 증상과 원인

처리 화면은 `job.progress`를 그대로 보여 준다. 워커는 STT 동안 75 → 90%를 흘리고, align 진입 90%, persist 95%, 완료 100%를 찍는다. **align 안에서는 진행 보고가 없었고, align은 수 분이 걸렸다.**

「제발 저에게 말할 시간을 주세요」 한 녹음의 align을 재 보니:

| | 값 |
|---|---|
| 임베딩 호출 | 11,157회 |
| 그중 서로 다른 스팬 | 403개 |
| align 소요 | 443초 |

`_smooth_backchannels`는 run 하나를 흡수할 때마다 처음부터 다시 훑는다(run 경계가 바뀌므로). 판정자 `make_embedding_arbiter`에는 캐시가 없어서, 유지로 판정된 run들이 재시작마다 다시 임베딩됐다 — 스팬당 평균 약 28회.

### 5.2 수정

- **판정자 캐시.** 스팬 → 임베딩 벡터를 캐시한다. 판정은 (자기, 이웃) 라벨 쌍마다 다르므로 벡터를 캐시하고 판정은 매번 계산한다. 결과는 바뀌지 않는다.
- **align 진행 보고.** `build_utterances(on_progress=...)`가 스무딩(0~80%)·조각 흡수(80~100%) 루프가 훑는 위치를 타임라인 비율로 알리고, 끝에 1.0을 보낸다. `progress.FractionProgress`가 이를 90 → 95%로 옮긴다 — 재시작으로 값이 뒤로 가면 최대값을 유지하고, 2초 간격으로 DB 쓰기를 줄이며, 끝은 항상 쓴다. STT 진행기처럼 매 보고마다 종료 요청을 확인한다.

### 5.3 결과

| | 수정 전 | 수정 후 |
|---|---|---|
| 임베딩 호출 | 11,157회 | **438회** |
| align 소요 | 443초 | **15.9초** |
| 진행률 | 90%에 고정 → 100% | 90 → 91 → 92 → 93 → 94 → 95% (약 3초 간격) |

두 측정 모두 다른 평가 작업과 CPU를 나눠 쓴 상태라 절대 시간은 실제보다 길다. 비율(약 28배)이 의미 있는 값이다.

## 5.5 pyannote 파라미터 조정 (채택 안 함)

남은 첫마디 누수가 pyannote 쪽 문제라면 파라미터로 줄일 수 있는지 쟀다. community-1의 조정 가능한 값은 네 개다.

| 파라미터 | 기본값 | 역할 |
|---|---|---|
| `clustering.threshold` | 0.6 | VBx 초기화용 1차 묶음(AHC)의 거리 기준 |
| `clustering.Fa` | 0.07 | VBx가 음향 특징을 얼마나 믿을지 — 높을수록 목소리 차이에 민감해 더 나눈다 |
| `clustering.Fb` | 0.8 | 화자 수 억제 — 낮을수록 화자를 쉽게 새로 만든다 |
| `segmentation.min_duration_off` | 0.0 | 같은 화자 구간 사이 이보다 짧은 공백을 메운다 |

`pipeline.training = True`로 두면 pyannote가 분할 신경망 출력과 임베딩을 캐시하므로(powerset 모델) 설정마다 클러스터링만 다시 돈다. 설정마다 현재 브랜치의 전체 처리(클러스터 병합 → 겹침 규칙 → 조각 흡수)를 적용해 채점했고, 기준 설정은 §4.5의 최종 수치를 4개 녹음 모두 소수점까지 재현했다. 2차에서는 `Fa`를 올려 생긴 과분할을 우리 클러스터 병합 기준(`cluster_merge` cos 0.85 → 0.75/0.65)이나 화자 수 힌트(5명)로 되돌리는 조합을 쟀다.

4개 녹음 평균 (주요 설정):

| 설정 | attr | head→prev | turn | 결과 화자 수 |
|---|---|---|---|---|
| **기준** | **90.36%** | 18.16% | **74.89%** | 5, 5, 5, 5 |
| threshold 0.5 / 0.7, Fb 1.5, 병합 0.75, 힌트 5 | 기준과 같음 | | | |
| min_duration_off 0.2 | 90.32% | 18.01% | 74.11% | 5, 5, 5, 5 |
| Fa 0.1 + 병합 0.75 | 90.25% | 18.48% | 74.42% | 6, 6, 5, 5 |
| Fa 0.15 | 87.87% | **15.56%** | 68.22% | 11, 10, 11, 12 |
| Fa 0.12 + 힌트 5 | 86.96% | 17.98% | 69.97% | 5, 5, 5, 5 |
| Fa 0.1 + 병합 0.65 | 73.94% | 20.51% | 62.00% | 5, 5, 4, 4 |

- **threshold·Fb·병합 기준 0.75·힌트는 기본 설정에서 결과를 바꾸지 않는다.** VBx가 같은 결과로 수렴하고, 이미 5명이라 병합·힌트가 할 일이 없다.
- **Fa를 올리면 첫마디 누수는 4개 녹음 모두 줄지만(평균 18.2% → 15.6%) 한 사람이 두세 라벨로 쪼개진다.** 분할 신경망은 전환을 어느 정도 잡고 있고, VBx가 그 짧은 구간들을 이웃 화자에 흡수하고 있다는 뜻이다.
- 쪼개진 라벨을 되돌리는 두 방법 모두 실패했다. 병합 기준을 0.65로 낮추면 서로 다른 사람까지 합쳐져 정확도가 16%p 무너지고(같은 회의 안에서는 서로 다른 사람의 centroid도 0.65를 넘는다), 화자 수 힌트는 pyannote가 VBx 결과 대신 KMeans로 다시 묶어 기준보다 나빠진다.
- **기본 설정을 유지한다.** 정확도를 지키면서 누수를 줄이는 조합은 없었다. 남은 누수를 줄이려면 파라미터가 아니라 다른 수단이 필요하다 — 분할 모델 자체(다른 diarization 모델), 또는 과분할 설정(Fa 0.15)의 짧은 구간을 전환 후보로만 쓰고 화자는 기준 설정에서 가져오는 식의 후처리. 둘 다 이번 범위 밖이다.

## 7. 남은 과제

1. **화자 전환 자체를 놓치는 경우**(§2.3)가 남은 누수의 주력이다. pyannote 파라미터 조정으로는 줄지 않았다(§5.5). 다른 diarization 모델, 또는 과분할 설정의 전환 후보를 쓰는 후처리가 다음 후보다.
2. **문장 단위의 부분 적용.** 문장부호가 확실하고 짧은(예: 15초 이하) 문장 안에서만 화자를 하나로 묶으면 11:48 같은 경우를 살릴 수 있을지 측정할 만하다.
3. **exclusive 출력과의 조합.** exclusive는 1단계 규칙 없이도 attr이 가장 높았다(90.33%).
4. **Whisper 단어 타임스탬프.** 턴 경계 근처에 길이 0인 단어(`41140–41140` 4개 연속 등)가 보인다.
